# 紅綠循環 (TDD)

TDD 就是**紅 → 綠**這條迴路。這個技能是讓那條迴路產出「值得留下來的測試」的參考：什麼算好測試、測試該放在哪、有哪些反模式、迴路的規則。每一節在每一次循環都適用——在迴路前與迴路中查閱，不是事後。

探索程式碼時先讀 `CONTEXT.md`（若存在），讓測試名稱與介面詞彙對齊專案的領域語言，並尊重這一區的 ADR。

## 什麼算好測試

測試驗證的是**透過公開介面觀察到的行為**，不是實作細節。實作可以整個換掉，測試不該跟著換。好測試讀起來像一份規格——「使用者可以用有效的購物車結帳」——一句話就講清楚存在哪個能力，而且能撐過重構，因為它不在乎內部結構怎麼長。

範例與 mock 的使用界線見 [resources/test-quality.md](resources/test-quality.md)。

## 接縫——測試放在哪

**接縫（seam）**是你下手觀測的公開邊界：能觀察到行為、又不用伸手進去內部的那個介面。測試住在接縫上，永遠不對著內部。

**只在事先講好的接縫上測。** 寫任何測試之前，先把要測的接縫寫下來、跟使用者確認。**沒確認過的接縫不寫測試。** 你不可能測完所有東西——事先講好接縫，是讓測試的力氣落在關鍵路徑與複雜邏輯上，而不是撒在每一個邊界情境上。

要問的問題是：「公開介面是什麼？我們該測哪幾個接縫？」

## 反模式

- **跟實作綁死**——mock 掉內部協作者、測私有方法、或從側門驗證（去查資料庫而不是用介面）。判斷方式：行為沒變、只是重構，測試就爆了。
- **同義反覆**——斷言用跟程式碼一樣的方式把預期值再算一次（`expect(add(a, b)).toBe(a + b)`、用手照同一套邏輯推出來的快照、把常數斷言等於自己），於是它天生就會過，永遠不可能跟程式碼意見相左。**預期值必須來自獨立的真實來源**——一個已知正確的字面值、一個手算過的例子、規格書。
- **水平切片**——先把測試全部寫完，再把實作全部寫完。整批寫出來的測試驗的是**想像中的**行為：你測到的是東西的**形狀**而不是使用者面對的行為，測試對真實變動變得不敏感，而且你在理解實作之前就把測試結構鎖死了。改成**垂直切片**：一個測試 → 一段實作 → 重複，每個測試都是一顆**曳光彈**，回應上一輪教會你的事。

## 迴路的規則

- **先紅後綠。** 先寫失敗的測試，再寫剛好夠讓它過的程式碼。不預測未來的測試，不加投機性的功能。
- **一次一片切片。** 一個接縫、一個測試、一段最小實作，就是一輪。
- **重構不屬於這條迴路。** 它屬於審查階段（見 `diff-review`），不在紅 → 綠的實作循環裡。

## 完成判準

每一個事先講好的接縫，都有至少一個先紅後綠的測試；沒有任何測試是在未確認的接縫上寫的。
