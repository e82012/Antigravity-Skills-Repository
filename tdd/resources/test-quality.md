# 測試品質與 mock 界線

[`tdd`](../SKILL.md) 的揭露參考。需要判斷「這個測試值不值得留」或「這裡該不該 mock」時翻。

## 好測試與壞測試的對照

| 面向 | 好 | 壞 |
|------|----|----|
| 名稱 | `使用者可以用有效的購物車結帳` | `test checkout 2` |
| 觀測點 | 公開介面的回傳值／副作用 | 私有方法、內部欄位、資料庫直查 |
| 預期值來源 | 已知正確的字面值、手算過的例子、規格 | 用跟程式碼同一套邏輯算出來 |
| 重構後 | 不動 | 爆掉，但行為根本沒變 |
| 失敗訊息 | 看得出哪個行為壞了 | `expected true to be false` |

## 判斷是不是壞測試的兩個問題

1. **我把實作整個換掉（行為不變），這個測試會爆嗎？** 會爆 → 跟實作綁死了。
2. **我把程式碼裡的 bug 種回去，這個測試會紅嗎？** 不會紅 → 它什麼也沒在守。

第二個問題就是**變異測試**的手動版。對關鍵路徑的測試，值得手動做一次：把 `>` 改成 `>=`、把 `+` 改成 `-`，看測試有沒有反應。

## mock 的界線

**預設不 mock。** 每一個 mock 都是一份「這個相依項會這樣行為」的假設，而假設會過期——被 mock 的那一端改了，測試照樣綠燈，然後正式環境炸掉。

| 對象 | 處置 |
|------|------|
| 純函式、值物件、領域邏輯 | 直接用真的 |
| 同一個程序內的協作者 | 直接用真的——mock 它就是跟實作綁死 |
| 資料庫 | 用真的（測試用資料庫／交易後 rollback／記憶體版本），不要 mock repository |
| 外部 HTTP API | 在 **HTTP 層**攔截（錄製過的 fixture），不要 mock 你自己的 client 類別 |
| 時間、亂數、UUID | 注入或凍結——這是最正當的 mock 用途 |
| 寄信、推播、金流等有副作用的外部系統 | 用假的實作（fake），不是 mock；斷言在「被要求做了什麼」上 |

**在 HTTP 層攔截，不要在你自己的 client 攔截**：前者連你的序列化、錯誤處理、重試邏輯一起測到；後者把這些全部跳過了。

## fake、stub、mock 的分別

- **fake**：有真實行為的簡化實作（記憶體版的 repository）。最耐用。
- **stub**：回固定值，不驗證互動。可接受。
- **mock**：驗證「某個方法被呼叫了幾次、帶什麼參數」。最脆——它斷言的是實作細節。只在「那次呼叫本身就是使用者要的行為」時用（例如：結帳成功時必須送出一封確認信）。

## 每個切片的檢查表

- [ ] 測試名稱講的是行為，不是函式名
- [ ] 測試寫在事先講好的接縫上
- [ ] 先看過它紅
- [ ] 預期值來自獨立的真實來源
- [ ] 只加了剛好夠讓它綠的程式碼
- [ ] 沒有為了測試而開的公開方法
