# 收斂成規格 (To Spec)

**這個技能不訪談。** 訪談是 `grill-with-docs` 的工作，這裡只把已經談成的東西整理成一份可交付的規格。如果對話裡還有沒解掉的決策，停下來說明是哪幾個，回去跑拷問，不要自己替使用者決定。

## 步驟

1. **讀設定**。讀 `docs/agents/flow-config.md` 取得議題追蹤系統的落點。檔案不存在就先跑 `setup-flow`。

2. **把對話收斂成規格**。用專案的領域語言寫（`CONTEXT.md`），不要另造詞。結構：

   ```markdown
   # <標題>

   ## 要解決的問題
   為什麼要做這件事。使用者看到的症狀或缺口。

   ## 範圍內
   這次要做到的行為，逐條列出。

   ## 明確不做
   刻意排除的東西。這一節比範圍內更重要——它擋掉範圍蔓延。

   ## 會動到的模組
   每個模組一行，寫它的介面會不會變。

   ## 事先講好的接縫
   哪幾個接縫要測。這一節直接餵給 `tdd`。

   ## 驗收條件
   可檢核的條件，一條一行。寫得出「怎麼驗」，不是「應該要正常運作」。

   ## 未解事項
   ⚠️ 標明查不到或還沒決定的，不要為了看起來完整而省略。
   ```

3. **只寫結論**。規格本體只寫「現在決定是什麼」，不寫「我們怎麼走到這」——推理過程留在對話裡。這與全局準則 §10 一致。

4. **發佈**。依 `flow-config.md` 的設定寫到議題追蹤系統或本地檔案。發佈後把位置（issue 連結或檔案路徑）回報給使用者。

## 完成判準

規格裡的每一個「範圍內」條目，都有對應的驗收條件；每一個「會動到的模組」，都講清楚介面變不變。做不到的條目標 ⚠️ 未解，不要留空。

## 接下來

多個 session 才做得完的工作 → `to-tickets` 切票。一個 session 做得完 → 直接 `implement`。
