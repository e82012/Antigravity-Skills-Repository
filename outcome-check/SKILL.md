# 產出裁判 (Outcome Check)

**教會 agent 自我批判很難；找一個全新 context、只帶驗收條件的裁判去實際操作產出，容易得多。** 這是本技能存在的唯一理由——寫程式的那個 agent 判自己做完了沒，是自我審計，獨立性為零；本技能要的是獨立性最大的那一端。

## 跟 `diff-review` 的分工

**裁判驗的是產出，`diff-review` 審的是 diff。** 兩者互補，不是二選一：

| | 看什麼 | 驗什麼 | 看不到什麼 |
|---|---|---|---|
| `diff-review` | 程式碼變更本身 | 有沒有照規範寫、有沒有忠實實作規格 | 產出實際運作起來對不對 |
| `outcome-check`（本技能） | 實際跑起來的產出 | 驗收條件逐條是否真的達成 | 產出完美但**過程**違規（亂改測試、繞過驗證） |

一次交付，兩者都跑：`diff-review` 抓「寫得對不對」，本技能抓「跑得對不對」。

## 步驟

### 1. 取得驗收條件（rubric）

優先順序：規格／工單裡的「驗收標準」欄位 → `feature-analysis-skill` 產出的驗收標準 → 使用者當場給的判準。**找不到就問使用者要，不准自己編一份「看起來合理」的驗收條件去驗**——那等於自己出題自己改考卷。

驗收條件要能拆成**逐條可操作**的檢查項，拆不開的先拆：「登入功能正常」不是一條驗收條件，「輸入正確帳密回傳 200 並帶 token」才是。

**不適用的情況**：沒有外部可觀察行為變化的改動（純重構、內部函式改名、型別調整）沒有東西給裁判操作，不要硬套本技能——用 `tdd` 既有測試驗證行為沒變就夠了。本技能只管**有行為要驗**的產出。

### 2. 派一個全新 context 的裁判

用 Agent 工具（或等效的 subagent 派工機制）另開一個 agent，**不是在當前對話脈絡裡自己判**。裁判只拿到兩樣東西：

- 逐條驗收條件（rubric）
- 產出的位置（服務網址、CLI 指令、資料表名稱）

**不給實作過程、不給推理脈絡、不給診斷紀錄。** 裁判是全新 context 的原因，就是要讓它不受「作者覺得自己做對了」這件事影響——它只認實際操作結果。

### 3. 裁判實際操作，不是重讀程式碼

依產出型態選操作方式，一律「像使用者一樣操作」，不是「像審查者一樣讀碼」：

| 產出型態 | 操作方式 |
|---|---|
| Web／前端 | 啟動服務，在瀏覽器裡走一次流程，看畫面與 console／network |
| API | 實際發 request，看 status code 與 response body |
| CLI／腳本 | 實際執行，看 stdout／exit code |
| 資料庫變更 | 實際查詢，確認資料真的落地、型別與約束正確 |
| 批次／排程 | 實際觸發一次，看執行紀錄與副作用 |

裁判看不到、也不需要看程式碼本身——它驗的是**行為**，不是**寫法**。

### 4. 逐條打分，回傳結構化結果

每一條驗收條件回傳三選一：**通過 / 不通過 / 無法判定**，「不通過」與「無法判定」都要附具體證據（實際輸出、截圖描述、查到的資料）。**完成判準**：rubric 有幾條，裁判就要交出幾條裁決，不能整體給一句「大致沒問題」。

### 5. 不通過就原封不動帶回去修

裁判的逐條缺失**原封不動**交回主線，不做二次摘要──摘要會把裁判抓到的具體證據磨損掉。主線修正後，重新走一次步驟 2～4。

**迭代上限**：連續 **3 輪**裁決仍未通過，觸發全局準則 §8 的停止條件——列出已嘗試的修法、可能原因、建議使用者介入的具體操作點，不要無限重跑。

## 完成判準

Rubric 的每一條都被裁判**實際操作**驗證過並留下證據；沒有任何一條是用「應該可以」帶過的。裁判的判定與理由完整附在最終回報裡，不摘要成一句「已驗收通過」。
