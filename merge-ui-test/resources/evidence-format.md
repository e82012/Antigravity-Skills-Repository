# 產物格式

落地位置依計畫書 §1.3，本檔只補「欄位怎麼填」。根目錄為
`C:\Users\user\Documents\整併\doc`。

## 1. 頁面文件 `doc/{站台代號}/{頁面名稱}.md`

四個部分依序為功能盤點、操作步驟、測試結果、觀察項。

### 新增：文件開頭的環境指紋

每份頁面文件開頭加一行環境指紋，供下次重放與跨站沿用判斷：

```md
環境指紋：前綴 `custom-modal-`（Notification 為 `ant-`）｜React 18 ＋ antd v5 cssinjs｜
viewport {w}×{h}｜盤點自 {網址}
```

前綴不同就代表**不能沿用另一站的選擇器**，這行是給下一個 session 的警示。

### §2 操作步驟：改為「自然語言 ＋ 定位錨點」

Re-test（計畫書 §7.4）與原站重放都要重跑同一串操作，純自然語言等於每次重新探索。
每個步驟補一欄定位錨點：

```md
| # | 操作 | 定位錨點 | 預期結果 |
|---|---|---|---|
| 1 | 玩家帳號填入 `smoke0908a` | `#memId` | 欄位顯示輸入值 |
| 2 | WM 百家樂限紅選「100 / 10k」 | `#data_WM_Baccarat` 所屬 `[class*=select-selector]` | 選中項顯示 `100 / 10k` |
| 3 | 按提交 | `button[type=submit]`（文字為「提 交」） | 送出 API 並跳轉 |
```

錨點優先序：**語意 `id`** > `type`／`name` > 去空白後的文字 > AX ref（ref 每次都會變，僅供當次使用）。

`rc_select_N`、`rc-tabs-N` 這類自動編號 id 跨渲染會變，**不算語意 id**，不可寫進操作步驟。

## 2. 總檢查清單 `doc/{站台代號}/{站台代號}總檢查清單.md`

格式依計畫書 §1.3.1，不重述。補以下填寫規則。

### 項目表格欄位

清單建立時就用六欄，不要等到階段 C 才補欄——事後補欄要重寫每一列。

```md
| 功能說明 | API | 判定 | 說明 | 與原站相比 | 差異說明 |
|---|---|---|---|---|---|
| 條件搜索 | `GET /api/member?memId=` | PASS | 完整值與部分字串皆可比對 | true | — |
```

前四欄為階段 B 的結果，後兩欄為階段 C 的結果，兩者互不覆寫。

「與原站相比」四個值：

| 值 | 意義 |
|---|---|
| `true` | 已於原站以相同條件執行，結果與合併站一致 |
| `false` | 已於原站以相同條件執行，結果不一致，差異寫入「差異說明」 |
| `未比對` | 尚未於原站執行（階段 C 未做到的項目一律填這個，不留空） |
| `⚠️` | 原站無法以相同條件執行（權限、資料或功能不存在），原因寫入「差異說明」 |

比對忽略計畫書 §5.4 的允許差異欄位（時間戳記、主鍵與 UID、token／簽章、分頁游標），
這幾項不同不算 `false`。

### 指標模式的填法（沿用同一張六欄表，不另開格式）

清單開頭先寫一行 `測試模式：指標模式`（或 `嚴謹模式`），讓讀者知道這批判定的深度。

| 欄位 | 指標模式怎麼填 |
|---|---|
| 判定 | 兩個指標的綜合結果（`PASS`／`FAIL`／`BLOCKED`／`⚠️`，定義見 `SKILL.md`） |
| 說明 | **指標 1（畫面操作）** 的證據：文字指紋 hash、清單筆數、選中值、導向 URL |
| 與原站相比 | **指標 2（API 回應）** 的結果，四個值沿用上表 |
| 差異說明 | 不一致的具體欄位或畫面差異 |

**被等價類合併掉的項目要留下涵蓋範圍**，否則讀者無法判斷哪些沒測：

```md
| 清單查詢 | `GET /api/member` | PASS | 涵蓋：條件搜索（完整值／部分字串／代理）、分頁、每頁筆數、狀態篩選 | true | 四組參數 hash 皆一致 |
```

跨頁同元件的第二頁寫成「與 {頁面} 同元件，已驗」，不重複列一整組。

升級嚴謹模式的項目，在說明欄標 **`[嚴謹]`**，讓讀者一眼看出哪幾項做了三層。

### 判定方向：一律以原站為基底

重構後的合併版常會多 select 幾個欄位、多回幾筆設定、多掛幾條路由。這些**不是不一致**。

判定順序固定兩步，不可顛倒：

1. **先查漏缺**——原站有的欄位、資料列、選項、端點，在合併站是不是一個不少？
2. **再看多出**——合併站多出來的部分，只記錄，不影響判定。

| 情況 | 判定 |
|---|---|
| 原站有、合併站缺 | `false` |
| 同一個項目，兩站的值不同 | `false` |
| 原站有的都在，合併站另有多出 | **`true`**（假性 `false`），多出的內容寫進「差異說明」 |

**先算差集再下判斷。** 只比總數或比 hash 會把「多出」誤判成「不一致」——
數量不同、hash 不同都只代表「有差異」，不代表「有漏缺」。

實測案例：`GET /api/config/actionTypeList` 合併站 133 筆、原站 126 筆，
第一眼判成 `false`；把原站的 126 筆逐一對進合併站發現一個不缺，多出的 7 筆是本站未啟用的功能類型，
依上表改判 `true`。同輪的 `GET /api/member/withdrawals` 合併站多兩個欄位，同樣判 `true`。

多出的部分仍值得寫進問題紀錄——它是可用性建議（使用者會選到永遠查不到資料的條件），
但不是資料不一致，兩者要分開講。

### 統計表格

統計表是判定 × 比對的二維表，一眼看得出「測過幾項」與「其中比對過幾項」：

```md
| 判定 | 項數 | `true` | `false` | `⚠️` | 未比對 |
|---|---|---|---|---|---|
| PASS | 85 | 0 | 0 | 0 | 85 |
| **合計** | **203** | **0** | **0** | **0** | **203** |
```

`N/A` 列同樣要有比對欄位——純前端項目雖不列入測試範圍，介面差異仍可能是合併造成的。

### 其他

- 以 JS 降級操作完成的項目，判定填 `⚠️`，說明欄寫「以 JS 降級操作，UI 層未驗證」。
- 統計數字實際數過，且用兩種數法交叉驗證；第一次就剛好吻合時換個範圍定義再數一次。
  兩個維度的合計要各自對得起來（判定合計＝比對合計＝總項數）。

## 2.5 合併結果指數（站台 README 的第一個區塊）

每個站台的 `doc/{站台代號}/README.md`，在標題與環境資訊登記表之間放一個「合併結果指數」。
它是**總檢查清單統計區的導出值**，不手填、不估算——數字對不上就是清單沒結清。

### 版面

```md
## 合併結果指數

| | |
|---|---|
| **總評** | **有條件通過** |
| 與原站一致率 | **94.6%**（227 / 240 項，其中 N/A 15 項） |
| 阻斷項 | **1 項**——{一句話寫是哪一項} |
| 信心度 | **中**——{一句話寫覆蓋缺口} |

| 維度 | 評級 | 依據 |
|---|---|---|
| API 回應一致（指標 2） | 🟢 通過 | |
| 畫面操作一致（指標 1） | 🟡 有條件 | |
| 資料正確性（DB 層） | 🟢 通過 | |
| 高風險 16 項 | 🟢 通過 | |
| 權限維度 | ⬜ 未覆蓋 | |

### 放行判斷

- 後端／資料層：{結論}
- 前端：{結論}
- 權限：{結論}
```

### 數字怎麼來

| 欄位 | 算法 |
|---|---|
| 與原站一致率 | 統計表的 `true` ÷ 總項數，取一位小數；括號內附原始分子分母與 `N/A` 項數 |
| 阻斷項 | `FAIL` 之中「功能完全不可用」的項數。`FAIL` 但仍可用（例如只差一個欄位）不計入 |

**不要自創加權總分。** 一致率是數得出來的，加權是拍出來的——拍出來的數字看起來精確反而更誤導。
維度用評級，不給分數。

### 維度評級的判準（四值，照著填，不自由心證）

| 評級 | 條件 |
|---|---|
| 🟢 通過 | 該維度沒有 `false`；或 `false` 全屬非資料面（訊息字串、錯誤碼、端點存廢、選單只多不少）且無阻斷項 |
| 🟡 有條件 | 有 `false` 但無阻斷項；或有阻斷項但根因已查明且確認可修 |
| 🔴 未通過 | 資料面不一致；或有阻斷項而根因未明 |
| ⬜ 未覆蓋 | 該維度沒有取得證據。**未覆蓋不可填 🟢** |

固定五個維度，前兩個就是指標模式的兩大指標。

### 信心度的判準

| 信心度 | 條件 |
|---|---|
| 高 | 主要角色層級皆已覆蓋，且 `BLOCKED` 為 0 |
| 中 | 只測過單一角色層級，或 `BLOCKED` 在 1–3 項 |
| 低 | `BLOCKED` 超過 3 項，或主要寫入路徑未執行 |

信心度講的是**這份結論可不可信**，不是合併站好不好，所以不折進一致率，另外列一行。

### 差異要標根因歸屬

README 另外放一張「差異的根因歸屬」表，每個 `false` 一列，寫落在前端還是後端，
以及**打了什麼、回了什麼**——判斷根因的方法見 `browser-recipes.md` §7.9。

## 4. 問題紀錄 `doc/畫面測試問題.md`

格式依計畫書 §7.2／§7.3，不重述。AI 撰寫時必附：站台代號與頁面網址、可直接照做的重現步驟
（帶定位錨點）、原站與合併站結果並列、證據檔路徑。

## 盤點要走完三層：清單、詳情、編輯

只掃清單頁的操作欄，會漏掉只存在於詳情頁的功能。

實測：玩家查詢與代理商查詢兩頁盤點完、階段 C 也比對完之後，回頭複查才發現
**「轉移代理商」根本不在清單**——它在詳情頁的「代理／所屬代理」欄位旁邊，
而且是個不可逆操作（會搬動帳務資料）。這種等級的功能漏記，等於整頁的盤點都不算完整。

每個頁面固定走三層，逐層記下功能：

| 層 | 要看什麼 |
|---|---|
| 清單 | 上方按鈕、搜索條件、表頭、**列操作欄的每一個圖示** |
| 詳情 | 頁首按鈕列、**每個欄位右側的行內動作**、分區塊的功能連結 |
| 編輯 | 進編輯模式後多出來的欄位與按鈕 |

判斷盤點完整性的訊號：**清單操作欄的圖示數量明顯少於這頁該有的功能數**時，
八成有功能藏在詳情頁。

## 「沒開彈窗」不等於「沒作用」

行內展開式的功能不會產生 `[class*=-modal-wrap]`。
只檢查有沒有彈窗就判定「按鈕沒反應」，會把正常功能記成缺陷。

實測：按「轉移代理商」後查彈窗得到 null，實際上是就地把欄位換成了下拉選單，
右側多出「確認轉移／取消」。

**比對點擊前後的頁面全文**，而不只看彈窗：

```js
const before = document.body.innerText.replace(/\s+/g, ' ');
// ...點擊...
const after = document.body.innerText.replace(/\s+/g, ' ');
before === after;   // true 才是真的沒反應
```
