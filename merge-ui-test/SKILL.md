# 合併專案畫面測試：瀏覽器操作層

## 本技能的定位

《260908合併專案畫面測試流程計畫書》（`C:\Users\user\Documents\260908合併專案畫面測試流程計畫書.md`）
規定**測什麼、怎麼判定**；本技能規定**怎麼操作**。兩者衝突時以計畫書為準。

**本技能不複述判定準則。** 判定值、階段定義、高風險 16 項、問題記錄格式一律回計畫書查。

驅動工具為 Claude Code 內建的 Browser pane（`mcp__Claude_Browser__*`），不是 Playwright。

## 開工前三件事（強制）

1. **讀計畫書**確認本輪屬哪個階段、需要哪幾層驗證。
2. **建立感知基準**：進站後先跑 `resources/browser-recipes.md` 的「環境探針」，把該站的
   元件前綴、viewport、框架版本記錄在頁面文件開頭。**不同站台前綴不同，不得沿用上一站的選擇器。**
3. **確認 pane 尺寸夠寬**。後台是 desktop 版面，pane 過窄會觸發 RWD，側邊選單以抽屜形式
   蓋住表單，所有點擊都會打在選單上。寬度不足時請使用者拉寬 Browser pane，不要硬點。

## 感知順序（由便宜到昂貴）

| 順序 | 工具 | 用途 |
|---|---|---|
| 1 | `javascript_tool` DOM 探針 | 元件盤點、狀態驗證、座標計算。最精確也最省 token |
| 2 | `read_page` `filter:"all"` | 拿 `ref`、看結構。**不要用 `filter:"interactive"`，會漏元件** |
| 3 | `get_page_text` | 確認文案、清單內容 |
| 4 | `read_network_requests` / `read_console_messages` | API 攔截與 error 蒐集 |
| 5 | `computer` screenshot | **只在需要當證據或比對版面時**。判讀畫面不靠它 |

`browser_batch` 是預設做法：可預測的連續動作壓成一次呼叫。單步呼叫只用在「下一步取決於上一步結果」。

## 流程

對應計畫書階段 A–E，各階段的瀏覽器操作配方見 `resources/browser-recipes.md`。

```
階段 A 盤點  → DOM 探針掃互動元素 → 產盤點表 → 等使用者確認
階段 B Smoke → 掛監聽 → 逐項操作 → 當場記錄
階段 C 比對  → 雙 tab 同條件重放 → API/UI/DB 三路比對
階段 D 高風險 → UI+API+DB 三層，缺一層標 ⚠️
階段 E 記錄  → 依計畫書 §7 格式寫入問題文件
```

## 硬性紀律

計畫書 §8 全數適用，本技能**增補三條**：

1. **降級操作必須標記。** 用 `javascript_tool` 直接改 DOM 或 dispatch 事件完成的操作，
   UI 層判定一律填 `⚠️` 並在說明欄寫「以 JS 降級操作」，**不得填 `PASS`**。
   API 層與 DB 層的判定不受影響——降級繞過的是 UI，不是後端。
2. **點擊必驗證，且驗證要另起一次呼叫。** React 18 批次更新，同一次 JS 執行內讀到的是舊值。
   「工具回報已點擊」不等於「頁面有反應」——必須讀出狀態變化才算數。
3. **點不到時走 `resources/troubleshooting.md` 的降級順序，同一元件失敗 3 次即停止**，
   標 `BLOCKED` 並輸出已嘗試清單，不得無限重試、也不得改用 JS 硬繞後填 `PASS`。
