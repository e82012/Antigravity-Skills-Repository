# 合併專案畫面測試：瀏覽器操作層

## 本技能的定位

驅動工具為 Claude Code 內建的 Browser pane（`mcp__Claude_Browser__*`）。

判定準則依測試模式分屬兩份文件，**同一件事只有一個出處，不重疊**：

| 模式 | 判定準則的擁有者 | 涵蓋範圍 |
|---|---|---|
| **指標模式**（預設） | **本技能 §指標判定** | 兩大指標的判定值、等價類劃分、不列入清單的項目 |
| **嚴謹模式** | 《260908合併專案畫面測試流程計畫書》（`C:\Users\user\Documents\260908合併專案畫面測試流程計畫書.md`） | 階段 A–E、三層驗證、高風險 16 項、問題記錄格式 |

**嚴謹模式的準則本技能一個字都不複述**，一律回計畫書查。
指標模式的準則計畫書沒有，只在本技能。兩者不會對同一件事有兩套講法。

## 兩種測試模式

**開工時使用者未指定 → 用指標模式**，並在回報的第一句寫明本輪用哪個模式。

### 指標模式（預設）

回答兩個問題，不做第三件事：

| # | 指標 | 通過條件 |
|---|---|---|
| 1 | **畫面操作是否一致** | 兩站執行同一操作後，UI 文字指紋一致，且關鍵狀態（清單筆數、選中值、彈窗開闔、導向 URL）一致 |
| 2 | **API 回應是否一致** | 兩站的 request（method／path 語意／payload）與 response（status／結構／業務值）一致 |

判定值只有四個：

| 判定 | 意義 |
|---|---|
| `PASS` | 兩個指標皆一致，且都取得證據 |
| `FAIL` | 任一指標不一致 |
| `BLOCKED` | 因環境、權限、資料而無法執行 |
| `⚠️` | 已執行但只拿到其中一個指標（例如攔不到請求），說明欄註明缺哪一個 |

**允許差異欄位沿用計畫書 §5.4**（時間戳、主鍵／UID、token、分頁游標）——這條屬計畫書所有，本技能只引用不重寫。

**指標模式不做 DB 層。** 需要 DB 佐證的功能一律升級嚴謹模式。

### 嚴謹模式

整套回計畫書執行。**下列情況強制升級，不由 AI 自行判斷可以留在指標模式：**

1. 屬計畫書 §6.2 高風險 16 項者。
2. 涉及金流、點數、權限的寫入端點。
3. 指標模式測出 `FAIL` 的項目——該項升級後重測，確認是合併問題還是既有 Bug。
4. 使用者指定。

## 等價類劃分（指標模式專用）

**測的是「有幾種行為」，不是「畫面上有幾顆按鈕」。** 同一個概念測一次就夠，第二次不會帶來新資訊。

同概念的判準（符合任一條即為同概念）：

| 判準 | 例子 | 怎麼做 |
|---|---|---|
| 同 API 端點、只換 query 參數 | 條件搜索／分頁／每頁筆數／狀態篩選 都是 `GET /api/member` | 合併成一項，**一次帶齊多組參數**驗證，說明欄列出實測過的參數組合 |
| 同前端元件跨頁重複 | 玩家查詢與代理商查詢是同一套 ProTable 工具列 | 第一頁測過就好，第二頁在說明欄註明「與 {頁面} 同元件，已驗」 |

**不算同概念，必須各測一次：**

- 相反語意的一組（開／關、啟用／停用、新增／刪除、設定／重置）
- 端點不同（`/api/member/check-account` 與 `/api/cagent/check-account` 是兩個概念）
- 同端點但業務語意不同（列內圖示開的彈窗與詳情頁開的彈窗，內容不同即分開）

## 不列入清單的項目（指標模式專用）

依計畫書 §4.5 的界線——**不發 API、且不改變畫面資料或 DB 狀態的操作，直接不列入盤點清單**，
不執行、不比對、也不佔一列 `N/A`。

包含：檔案匯出與下載、清單顯示設定（欄位設定、顯示密度）、單純的表單欄位填寫、
剪貼簿操作、前端計算與提示。

**界線在 API 不在元件**：同一顆按鈕若同時改查詢參數並送出請求，仍要測。

實測依據：某輪 82 個判定項目中有 15 項屬此類，全部執行並做了兩站 hash 比對，
最後判定填 `N/A`（＝不列入範圍）——**工作全做了，結論是不用做。**

## 環境前置條件（開工前先跟使用者確認，不靠工具硬撐）

這兩項不成立時**整輪測試不要開始**，先請使用者處理：

| 前置條件 | 為什麼 | 不成立的症狀 |
|---|---|---|
| **Claude 視窗在前景、不被其他視窗遮蔽** | 視窗被蓋住時頁面完全不繪製 | `innerWidth`／`innerHeight` 讀成 `0`，RWD 以極小螢幕掛載，整個搜索條件區消失 |
| **Browser pane 夠寬（實測 1042×922 順暢）** | 後台是 desktop 版面 | 觸發 RWD，側邊選單變抽屜蓋住表單，所有點擊打在遮罩上 |

`resources/browser-recipes.md` §1.5 的截圖強制繪製配方是**異常處理**，不是常態流程。
實測一輪測試曾為此多燒 47 張救援截圖與相應回合——**環境弄對比事後補救便宜一個數量級。**

## 開工前三件事（強制）

1. **確認本輪模式**。指標模式**不需要讀計畫書**——判定準則在本檔，讀了只是多灌 context
   （實測計畫書一次載入約 21.6K 字元）。嚴謹模式才讀，且只讀本輪用得到的階段章節。
2. **建立感知基準**：進站後先跑 `resources/browser-recipes.md` 的「環境探針」，把該站的
   元件前綴、viewport、框架版本記錄在頁面文件開頭。**不同站台前綴不同，不得沿用上一站的選擇器。**
3. **一次 `read_page` `filter:"all"` 取回整頁 ref**，當作這一頁的操作索引反覆使用，
   直到 `navigate` 為止。ref 點擊不需截圖、不需座標換算，是最省回合的操作路徑。

## 工具選用：分「要操作」與「要讀取」兩條線

**要操作元件（點、填、選）——ref 優先：**

| 順序 | 手段 | 每次操作的回合成本 |
|---|---|---|
| 1 | `read_page` `filter:"all"` 取到的 `ref` → `computer` 點擊 | **1**（ref 已在手上，直接點） |
| 2 | DOM 探針算座標 → `screenshot` → 座標點擊 | **3**（取座標、截圖、點擊，且狀態一變就要重取） |
| 3 以下 | 鍵盤路徑、JS 合成事件 | 見 `resources/troubleshooting.md` 降級順序 |

**ref 是預設路徑，座標是 ref 取不到時的備案。** 實測一輪測試 277 次點擊全走座標路線、
`read_page` 一次都沒用，光這條就多燒 139 張前置截圖。
ref 失效的時機只有兩個：`navigate` 之後（重新編號）、捲動之後（座標不更新）——
兩者都只要重跑一次 `read_page` 就補回來，不必整輪改走座標。

**要讀取狀態（驗證、盤點、比對）——JS 探針優先：**

| 順序 | 工具 | 用途 |
|---|---|---|
| 1 | `javascript_tool` DOM 探針 | 狀態驗證、元件盤點、內容比對。最精確也最省 token |
| 2 | `get_page_text` | 確認文案、清單內容 |
| 3 | `read_network_requests` / `read_console_messages` | API 攔截與 error 蒐集 |
| 4 | `computer` screenshot | **只在需要當證據或比對版面時**。判讀畫面不靠它 |

`browser_batch` 是預設做法：可預測的連續動作壓成一次呼叫。單步呼叫只用在「下一步取決於上一步結果」。

## 流程

### 指標模式

```
1 盤點   → DOM 探針掃互動元素 → 套等價類劃分與不列入規則 → 產概念清單 → 等使用者確認
2 逐概念 → 合併站操作 → 攔下真實請求 → 原站原封不動重放 → 兩指標當場判定
3 歸因   → 每個 false 判前端或後端（recipes §7.9），結論進 README 的「差異的根因歸屬」表
4 收斂   → FAIL 的項目升級嚴謹模式重測；其餘寫入頁面文件與總清單，更新站台 README 的合併結果指數
```

第 2 步的交錯做法見 `resources/browser-recipes.md` §7.3——**比對參數直接來自合併站的真實操作**，
兩站條件天然一致，不必另外設計。

### 嚴謹模式

對應計畫書階段 A–E，各階段的瀏覽器操作配方見 `resources/browser-recipes.md`。

```
階段 A 盤點  → DOM 探針掃互動元素 → 產盤點表 → 等使用者確認
階段 B Smoke → 掛監聽 → 逐項操作 → 當場記錄
階段 C 比對  → 雙 tab 同條件重放 → API/UI/DB 三路比對
階段 D 高風險 → UI+API+DB 三層，缺一層標 ⚠️
階段 E 記錄  → 依計畫書 §7 格式寫入問題文件
```

## 硬性紀律

計畫書 §8 在兩種模式下皆適用，本技能**增補八條**：

1. **降級操作必須標記。** 用 `javascript_tool` 直接改 DOM 或 dispatch 事件完成的操作，
   UI 層判定一律填 `⚠️` 並在說明欄寫「以 JS 降級操作」，**不得填 `PASS`**。
   API 層與 DB 層的判定不受影響——降級繞過的是 UI，不是後端。
2. **點擊必驗證，且驗證要另起一次呼叫。** React 18 批次更新，同一次 JS 執行內讀到的是舊值。
   「工具回報已點擊」不等於「頁面有反應」——必須讀出狀態變化才算數。
3. **點不到時走 `resources/troubleshooting.md` 的降級順序，同一元件失敗 3 次即停止**，
   標 `BLOCKED` 並輸出已嘗試清單，不得無限重試、也不得改用 JS 硬繞後填 `PASS`。
4. **一個功能項目的回合預算是 3 回合。** 取 ref／設定條件 → 操作 → 驗證，超過就停下來想
   「是不是在逐欄做本來可以一批做完的事」。同一可視區內的多個目標一次填完、
   同一頁的 ref 取一次用到底、驗證與 API 攔截壓在同一次呼叫裡。
   實測 `browser_batch` 平均每批只塞 5.3 個動作、中位數 4，批次化的空間並沒有吃滿。
5. **模式不得中途默默切換。** 指標模式遇到強制升級條件時，**明說「本項升級嚴謹模式」再往下做**，
   不得用指標模式的證據填嚴謹模式的判定，也不得為了省事把該升級的項目留在指標模式。
6. **每個 `false` 都要判根因，不判不寫問題單。** 比對出差異只完成一半——同一個畫面差異，
   根因在前端或後端，處置對象與嚴重度完全不同。三種探法見 `resources/browser-recipes.md` §7.9，
   結論寫進站台 README 的「差異的根因歸屬」表，每列註明打了什麼、回了什麼。
7. **收工要產出合併結果指數。** 站台 README 的第一個區塊，格式與判準見
   `resources/evidence-format.md` §2.5。一致率由總清單統計區導出、不手填；維度只給評級不給分數，
   **不自創加權總分**；覆蓋缺口列為「信心度」另計，不折進一致率，未取得證據的維度標 ⬜ 未覆蓋、不得填 🟢。
8. **不可逆操作照做。** 計畫書 §3.3 已規定測試站的 CRUD 一律實際執行；
   「功能自己跳警語說無法撤銷」「會影響其他資料」「沒有原始檔可還原」**都不是略過的理由**。
   把警語與現況記成證據，然後執行。唯一例外是本機代理的憑證類硬性限制（輸入密碼、建立帳號），
   那類標 `BLOCKED` 並寫明需人員執行，不得擴大解釋到其他功能。
