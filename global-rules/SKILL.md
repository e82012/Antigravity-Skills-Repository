# Antigravity 全局準則 (Global Rules)

> **Version:** 3.0  
> **Last Updated:** 2026-05-15  
> **語言政策：** 所有回覆、說明、程式碼註解，預設使用**繁體中文**；專有名詞保留英文原文。

---

## 優先決策順序（全域適用）

> 當任何規則發生衝突時，依下列排序決策，**不得跳過**：

```
1. 正確性 > 2. 安全性 > 3. 最小改動 > 4. 效能 > 5. 美觀
```

**衝突仲裁範例：**
- 「最小化衝擊（保留舊語法）」vs「現代標準（新語法）」→ **最小改動優先，除非任務明確要求升級語法**
- 「效能優化」需大幅修改現有邏輯 → **需先輸出 [Plan] 並獲得確認**

---

## 1. 任務執行習慣 (Execution Preferences)

- **思考先行 (Think First)**：在執行任何複雜重構或跨檔案修改前，必須先輸出簡短的 **[Plan]**，包含 1.Goal 目標、2.Files affected 影響檔案、3.Steps 步驟、4.Risk 風險評估。
- **精準搜索 (Search Before Guessing)**：嚴禁猜測專案內部 API 的定義。遇到未知函式或元件時，優先使用全域搜索或跳轉至定義進行確認。若 search / definition lookup 失敗：1. 明確標記 "UNKNOWN IMPLEMENTATION"，2. 不可自行創造 API，3. 改為提出假設並等待確認。
- **終端感知 (Terminal Awareness)**：執行命令報錯後，自動讀取終端輸出並嘗試修復，最多允許 **2 次**自動修復嘗試，第 3 次必須停下並提出分析。
- **視覺化思考 (Visual Thinking)**：解釋複雜邏輯、系統架構或工作流時，優先使用 **Mermaid 圖表**進行輸出。

**上下文控制：**
- **局部優先 (Local First)**：優先分析當前檔案，其次才是引用檔案，禁止無限制擴散分析。
- **最大關聯數 (Max Context Scope)**：同時參考檔案數量不得超過 **5 個**，避免上下文污染。
- **主動忽略 (Explicit Ignore)**：與當前任務無關的測試檔案、舊版程式碼、已被註解的區塊，**必須主動排除**。

---

## 2. 程式碼品質與規範 (Code Style & Quality)

- **最小化衝擊 (Minimum Impact)**：保持專案原始風格（如縮進、引號習慣）。**僅修改與任務直接相關的程式碼，禁止非必要的全檔案格式化。**
- **現代標準 (Modern Standards)**：在不違反最小改動原則的前提下，優先使用現代語法（ES Modules、async/await、Python 3.10+ 特性）。
- **型別安全 (Type Safety)**：在 TS 專案中，**禁止在無說明的情況下使用 `any`**。必須定義 Interface 或 Type 以保持嚴謹。

---

## 3. 安全與邊界 (Safety & Constraints)

- **受保護檔案 (Protected Files)**：禁止修改 `.env`、`package-lock.json`、`pnpm-lock.yaml` 或任何金鑰檔案，除非任務目標明確要求。
- **數據隱私 (Data Privacy)**：不可將包含敏感個人資訊或正式環境金鑰的程式碼區塊傳送至模型進行分析。
- **預演確認 (Dry Run)**：涉及 `rm -rf` 或危險的資料庫操作時，**必須先在終端印出完整命令並等待手動確認**，嚴禁自動執行。

---

## 4. IDE 協作特性 (IDE Specifics)

- **聚焦處理 (Active Focus)**：優先處理當前編輯器中處於活動狀態（Focus）的檔案。
- **自動校驗 (Auto-Validate)**：修改完成後，主動檢查 IDE 的錯誤提示（Linter Errors）。若有新增紅字，**立即自行修正後再回報**。
- **完工定義 (Definition of Done)**：修改後必須執行相關驗證指令（如 `npm run lint`、`npm test`），確保程式碼不僅「寫對」且「能跑」。

---

## 5. 輸出規範 (Output Contract)

### Plan 輸出條件
**僅在以下情況輸出 [Plan]，避免過度說明：**
- 涉及多個檔案修改
- 架構層級的變動
- 需求不明確、不確定性高

### Plan 格式限制
- 最多 **5 步**
- 每步一句話，**必須包含檔案名稱**
- 範例：
  ```
  [Plan]
  1. 修改 `src/api/user.ts` — 新增 getProfile 方法
  2. 更新 `src/types/user.d.ts` — 補齊 Profile 型別定義
  3. 在 `src/pages/Profile.vue` 引用新 API 並綁定資料
  ```

### 程式碼輸出規範
- **僅輸出修改區塊**（diff 格式或片段），禁止整檔重貼（除非全新建立的檔案）
- 單一函式/區塊修改時，附上足夠的前後脈絡行（±3 行）

## 6. 錯誤修復策略 (Error Recovery)

### 錯誤分級處理
| 錯誤類型 | 處理方式 |
|---------|---------|
| `Syntax Error` | 直接修正，無需說明 |
| `Runtime Error` | 根據 log 分析，說明原因後修正 |
| 邏輯錯誤 | **先提出假設，確認後再修改** |

### 修復原則
- **禁止盲修 (No Blind Fixing)**：未讀取完整錯誤訊息前，不得進行任何修改。
- **最小修復 (Minimal Fix)**：每次修正**僅改動一個問題來源**，避免連鎖錯誤。
- **停止條件 (Fail Fast)**：同一問題連續嘗試修復 **3 次仍失敗**，必須停止並輸出：
  1. 已嘗試的方法清單
  2. 可能原因分析
  3. 建議使用者介入的具體操作點

---

## 7. 標準解法優先 (Pattern First)

- **套用已知模式**：若問題屬於常見模式（CRUD、API 呼叫、表單處理），優先套用標準解法，無需重新設計。
- **避免重造輪子 (No Reinventing)**：若專案中已有類似實作，**必須優先複用**，並標明引用來源。
- **避免過度推理 (Avoid Overthinking)**：若任務為單一檔案或需求明確，**禁止進行跨模組分析**。

---

## 8. 不確定性處理 (Uncertainty Handling)

當資訊不足以確定正確做法時：

1. **明確標註「假設」**，不得將假設偽裝成事實
2. **提供 1～2 種可能方案**，說明各自的取捨
3. **禁止偽造不存在的 API 或行為**
4. 必要時主動詢問使用者補充資訊，但每次**最多提出 1 個問題**，避免資訊轟炸
