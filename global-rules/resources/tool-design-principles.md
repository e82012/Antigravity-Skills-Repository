# 小工具設計前提

> 決定「該不該做這支工具」與「做出來合不合格」的判準。動手前逐條問一次，做完再逐條驗一次。
> 這份是「用到再查」的參考知識，不隨 session 全載；既有工具清單建議維護在專案自己的入口檔速查表。

## 為什麼要有這份

工具化的目的是把**重複的機械流程**收成一行，省下反覆重寫指令的往返。但工具一旦判錯、或被誤當成權威，代價比手動高得多——手動出錯只錯一次，工具出錯會**每次都錯，而且沒人再去檢查**。

所以門檻不是「能不能寫出來」，是「寫出來之後，還能不能信任它的輸出」。

## 一、該不該做：三個門檻，缺一不可

### 門檻 1：這件事真的重複發生

- ✅ 已經**實際做過三次以上**，且每次流程幾乎相同
- ❌ 「以後可能會常用」——沒發生過的重複不算重複
- ❌ 一次性的批次處理：寫個腳本跑完就刪，不要留成工具

判準：**舉得出前幾次是什麼時候做的**。舉不出來就還不到時候。

### 門檻 2：判準完全客觀

工具算出來的答案就是最終答案，不需要人再判斷一次。

- ✅ 字串比對、數字比較、檔案存在與否、hash 相同與否
- ❌ 「這段寫得好不好」「該不該刪」「要不要改」——凡是答案取決於情境的，都不行

判準：**同樣的輸入，換一個人來判斷會不會得到不同答案**。會，就不該工具化。

### 門檻 3：不會取代思考

工具負責**蒐集事實**，判斷仍留給人。

- ✅ 報告「這個檔沒有 metadata 區塊」——這是事實
- ❌ 直接補上 metadata——「該不該有」是判斷，不是事實
- ❌ 把需要判讀的環節自動化：例如把「驗證規則是否生效」包成一鍵，會讓人跳過判讀回覆內容這一步，把「沒報錯」當成「有生效」

判準：**如果工具的輸出被完全照做，會不會出事**。會，就要重新設計成「只報事實」。

> 真正的成本往往不在跑指令。若一件事有 90% 的心力花在設計與判讀、只有 10% 在執行，工具化省不了多少，卻可能讓人跳過那 90%。

## 二、做出來要符合：五條硬性要求

### 1. 錯誤一定要回非 0 退出碼

PowerShell 的裸 `throw` 在 `pwsh -File` 下**會回 exit 0**。自動化呼叫者看到 0 就當成功往下走——備份工具若這樣，會讓人在「以為有備份」的狀態下改檔。

一律用顯式 `exit N`，並在 README 列出每個碼的意義與呼叫端該怎麼辦。

### 2. 寧可漏報，不可誤報

假陽性比假陰性更傷：**一份會亂喊的工具，讀的人很快就全部略過，等於沒做。**

不確定的情況一律排除，並在 README 寫明「刻意不檢查什麼、為什麼」。讀者需要知道工具的沉默不代表沒問題。

### 3. 改既有檔案前必須可回復

會寫入既有檔案的工具，動手前要先備份，或至少提供 `-DryRun` 讓人先看會改什麼。

全新產生的檔案不受此限。

### 4. 路徑參數要防 shell 吃掉

從 Bash 工具呼叫時，未加引號的 `\` 會被吃掉（`d:\proj` → `d:proj`），參數綁定靜默失敗。所有吃路徑的工具都要偵測並回 `exit 4`，附上修法提示。

作法：收到路徑後檢查「該含的路徑分隔符是否消失」，判定被吃掉就中止，並印出正確寫法（加引號或改用正斜線）。

### 5. 登記進速查表

專案入口檔裡的「本機工具速查」表是新 session 唯一會全載的工具清單——**沒列進去的工具等於不存在**，下一個 session 不會知道它，還可能重造一個。

## 三、做完之後：驗收清單

逐項實測，不憑印象：

- [ ] **正常流程**跑得通
- [ ] **每個錯誤路徑**都回正確的非 0 退出碼（缺參數、路徑不存在、目標不存在⋯）
- [ ] **用真實案例回測**：拿過去實際發生過的問題餵進去，確認抓得到（驗漏報）
- [ ] **對乾淨的輸入零發現**（驗誤報）
- [ ] **失敗時不留半成品**（中途出錯要回滾）
- [ ] README 寫明：用法、每個退出碼、**刻意不做什麼**
- [ ] 已登記進專案入口檔的速查表
- [ ] 開全新 session 驗證：它找得到這支工具嗎？會不會盲信輸出？

最後一項最容易被跳過，卻最重要——工具的價值取決於後人會不會正確使用它，那不是作者自己說了算。

## 四、判斷失敗的例子（真實案例）

| 提案 | 卡在哪 | 結論 |
|------|--------|------|
| 一鍵驗證規則是否生效 | 門檻 3：出題與判讀回覆才是主要工作，自動化會讓人跳過 | 不做 |
| 自動清理暫存檔 | 門檻 2：「哪些能刪」取決於情境，不是機械規則 | 不做 |
| 包一層 `git worktree remove` | 門檻 1：內建指令本身就是工具，包裝救不到「壓根沒想到要用」的情況 | 不做 |
| 包一層 `gh` 送出 body | 門檻 3：錯誤發生在「怎麼組指令」，包裝只是換個地方犯錯 | 不做 |

> 結論是「不做」的提案，同樣值得記下來——否則下次會再想一遍。
