# 查證深度規則：如何驗證「A 依賴/對應/影響 B」這類宣稱

## 適用範圍

任何需要驗證「A 跟 B 有沒有關聯」的場合都適用，不限於某個特定任務或某份 SOP：
code review、debug、影響範圍分析、讀文件抓矛盾、查證他人產出的文件或報告等。

## 背景：一次真實的失手

查證一份 AI 產出的技術文件時，文件宣稱「`service_status` 這張資料表，對應
`service:start`/`service:stop` 這兩個排程指令的邏輯」。查證時只確認了：
這兩個指令確實存在、確實有註冊排程——就判定這句話「正確」。

但實際打開這兩個指令的程式碼一讀，裡面從頭到尾操作的都是另一張表（`ServiceRegistry`），
完全沒有引用宣稱中的那張表。「兩者都存在」不代表「兩者有關聯」，這中間的因果關係
從頭到尾沒有被真的檢查過。

同一次查證裡還有一個數字問題：文件說「共 205 個檔案」，查證時只算了最外層目錄
（剛好也是 205 個），沒發現底下還有三個子目錄、裡面還有其他檔案，遞迴總數其實是
222 個。兩個錯誤湊出一個看似正確的答案，純屬巧合，範圍認知從頭到尾沒有對齊過。

## 這是什麼問題（辨識用）

下次遇到類似情境，先問自己「我現在是不是在犯這五個錯誤之一」：

1. **只驗證間接證據，沒驗證直接證據**：A 存在、B 存在、A 有跟 B 同時出現的脈絡
   （同一個排程檔、同一份文件、同一個目錄），都只是間接證據。直接證據是「A 的
   程式碼本體裡，真的呼叫/引用/查詢了 B」。名稱像、時間點同時發生、待在同一個
   檔案附近，都不能取代讀一次呼叫鏈。
2. **巧合正確掩蓋範圍認知錯誤**：算出來的數字剛好跟宣稱一致時，要先確認「我算的
   範圍」跟「宣稱指涉的範圍」是不是同一件事，不能因為數字對上就直接判定為證實，
   否則下次範圍條件一變，這個「證實」馬上失效。
3. **找到第一個支持的證據就停手**：查證的目的是「嘗試推翻宣稱」，推翻不了才算
   通過，不是「找到一個看起來支持的線索就結案」。找到支持證據後，要主動再問一次
   「有沒有反例？」，而不是收工。
4. **拿「相關的數量」當「要處理的數量」**：掃出「有某特徵」的一批東西，就直接當成
   工作量去估規模、去派工。但有特徵只代表進入候選集，真正的門檻條件（超過幾條、
   真的壞掉、真的要改）通常會篩掉一大半。數字沒算錯，是**條件問錯了**。
5. **規則只在某個章節/情境裡才想得起來用**：「要讀程式碼本體，不能只看名稱」這種
   原則是通用的，不會因為現在查的是「資料庫」還是「API」還是「排程」而不適用。
   看到「A 對應/依賴/影響 B」這種句型，不管出現在哪個主題底下，都要套用同一套
   查證動作。

## 具體行為準則（做法，不只是提醒）

**規則一：宣稱「A 對應/依賴/使用/影響 B」時，必須讀 B（或 A）程式碼本體裡實際的
呼叫/查詢/引用邏輯，不能只驗證 A、B 兩者各自存在。**

驗證步驟幫固定是三步，缺一不可：
1. 確認 A 存在（最容易做到，但只做到這步等於沒查證）
2. 確認 B 存在
3. **打開 A（或 B）的原始碼，找到那一行實際操作 B（或 A）的程式碼**，把這行貼出來
   當作證據。如果找不到這一行，即使 1、2 都成立，也要判定為「查無實質關聯」或
   「錯誤」，不能因為 1、2 成立就腦補 3 也成立。

**規則二：任何統計數字（檔案數、行數、路由數……）核對前，先確認清楚「宣稱的數字
指涉的範圍」跟「我要拿去比對的範圍」是不是同一個定義。**

具體做法：
- 先問「這個目錄底下有沒有子目錄／這個清單有沒有排除條件／這個統計有沒有可能用
  遞迴或非遞迴兩種算法」，把可能的範圍歧義先列出來，不要跳過這步直接開始數。
- 如果第一次算出來的數字剛好跟宣稱吻合，**這時候反而要提高警覺**，多做一次
  「換一種範圍定義會不會得到不同數字」的檢查，因為巧合吻合往往代表兩邊都用了
  相同的簡化假設，而不是真的驗證過。

**規則三：驗證一個宣稱時，找到第一個支持證據後，追加問自己一句「這個證據能不能
被推翻／有沒有反例？」，再決定是否收斂成最終判定。**

具體做法：
- 找到「A 存在」之後，不要停，繼續問「這個存在的 A，真的做了宣稱說的那件事嗎？」
- 如果查證任務有固定輸出格式（例如「證據 → 判定」），寫判定前重讀一次自己蒐集的
  證據，確認證據裡沒有可以推翻判定的內容被自己忽略掉。

**規則四：估算規模或派工前，先驗證「符合處理條件的數量」，而不是「與主題相關的
數量」——兩者差距往往是數倍。**

規則二治的是「數字算錯」（範圍漏算子目錄）；這條治的是「數字算對、但條件問錯」。
數字本身正確，卻不是任務真正要處理的那一群，照樣導致整個計畫失準。

具體做法：
- 動手數之前，先把任務的**處理條件**寫成一句可驗證的判斷式（例：「變更記錄超過
  5 條」），再照那句話去數；不要用「跟這件事有關的檔案」這種寬鬆條件代替。
- **相關 ≠ 符合條件**：有某個特徵（有變更記錄區塊、有呼叫某函式、檔名含關鍵字）
  只代表「進入候選集」，還要再過一次真正的門檻條件才算數。
- 數完後反問一句「這批裡面有多少其實**本來就合格、不用動**？」。如果答不出來，
  代表數的是候選集不是工作集。
- 規模會決定要不要拆工、拆給幾個人。**先驗條件再定規模**，不要先宣布派工計畫再
  回頭補查——計畫一旦公布，錯誤的規模會連帶決定錯誤的分工與時程。

**規則五：把查證方法本身當成跨情境的通用技能，不要因為換了主題（從查 API 換成查
資料庫、從查 middleware 換成查排程）就以為原則不適用。**

具體做法：
- 每次要下判定前，先在心裡確認一句抽象句子：「我今天驗證的是『A 對應 B』，
  不管 A、B 具體是什麼型態（表、路由、指令、設定），驗證方法都一樣：讀 B 的
  程式碼本體找那一行實際操作 A 的證據。」
- 不要因為手上這份 SOP／checklist 是為某個特定任務寫的（例如「Migration 欄位
  查證」），就把「讀程式碼本體」這種通用原則誤解成「只在查 migration 欄位時
  才要做」。

## 一句話速記

**「A 存在、B 存在、A 跟 B 有出現在一起」≠「A 真的用了 B」。看到『對應/依賴/使用/
影響』這種字眼時，去讀那一行真正做這件事的程式碼，不要用兩者的存在性互相佐證。**

**「有這個特徵」≠「需要處理」。估規模、派工前，先照真正的門檻條件數一次，
不要拿候選集當工作集。**
