# 功能需求分析與改善建議準則 (FA Skills)

> **Version:** 1.0
> **Last Updated:** 2026-06-10
> **基礎依賴：** `global-rules` — 型別安全、最小化衝擊、錯誤修復策略等基礎規範
> **定位：** 針對「新功能需求」或「現有功能改善」時，產出分析報告與建議的判斷準則

---

## 1. 分析流程框架 (Analysis Process)

### 思考順序

依下列順序進行，**不得跳過前項直接輸出後項**：

```
1. 問題確認 → 2. 現況盤點 → 3. 影響範圍評估 → 4. 方案建議 → 5. 優先級排序 → 6. 風險提示
```

- **問題確認**：先搞清楚「這個需求/改善在解決什麼真實痛點」，再討論怎麼做。沒有痛點的需求不值得分析。
- **範圍控制**：聚焦於當前提案範疇，延伸議題以 `[IDEA]` 標註，不混入主線建議。

### 輸入類型判斷

| 輸入情境 | 對應行動 |
|---------|---------|
| 需求描述模糊、背景不足 | 先列出缺口，標註 `[NEED_INFO]`，提出釐清問題 |
| 單一功能點的改善討論 | **結論優先**，附簡短分析與建議 |
| 多方案選型比較 | **比較表 + 明確推薦**，說明選擇理由 |
| 全新功能提案 | **完整分析結構**，含影響範圍與實作建議 |
| 現有功能的 Bug 或體驗問題 | **根因分析 + 改善方向**，區分治標與治本 |

## 2. 需求釐清 (Requirement Clarification)

### 必問三題

拿到任何功能需求或改善提案，先回答：

| 問題 | 說明 |
|------|------|
| **解決誰的問題？** | 使用者角色、情境、頻率。內部系統還是終端用戶？ |
| **現在怎麼解決的？** | 現有流程或 workaround 是什麼？為什麼不夠好？ |
| **成功長什麼樣？** | 完成後可以被驗證的具體指標，而非「更好用」這種空話 |

### 常見需求陷阱

| 陷阱 | 說明 |
|------|------|
| **解法包裝成需求** | 「我需要一個彈窗」→ 真正需求可能是「我需要使用者確認某動作」 |
| **範疇蔓延** | 「順便也做一下 OOO」— 每個順便都要重新評估成本 |
| **沒有優先級** | 全部都很急 = 全部都不急，必須逼出排序 |
| **假設用戶行為** | 「使用者一定會先看這裡」— 沒有數據前都是假設 |

## 3. 現況盤點 (Current State Assessment)

分析改善需求前，必須先描述現況，包含：

- **現有功能行為**：目前系統/功能的實際運作方式
- **已知問題**：具體的缺陷、體驗問題或效能瓶頸
- **影響範圍**：此功能牽涉哪些模組、API、資料表、使用者流程
- **數據佐證**（若有）：錯誤率、用戶回報頻率、效能指標等

### 影響範圍評估標記

| 範圍等級 | 定義 | 注意事項 |
|---------|------|---------|
| 🟢 **局部** | 單一元件或畫面，無跨模組影響 | 低風險，可快速迭代 |
| 🟡 **中度** | 跨多個元件或共用邏輯 | 需評估相依模組的副作用 |
| 🔴 **廣泛** | 核心流程、共用服務、資料結構異動 | 必須完整測試，謹慎上線 |

---

## 4. 方案建議 (Solution Recommendation)

### 建議原則

- **最小有效解優先**：能用最小改動解決問題，就不要大動干戈
- **治本 vs 治標要分清楚**：治標方案可以快速上線止血，但治本方案才是目標，兩者要分開說明
- **不推薦沒把握的方案**：技術不確定性高的方案必須標記，並建議先做 PoC 驗證

### 方案比較格式

```
## 方案比較

| 方案 | 開發成本 | 影響範圍 | 可維護性 | 風險 | 推薦度 |
|------|---------|---------|---------|------|-------|
| 方案 A | 低 | 局部 | 高 | 低 | ⭐⭐⭐ |
| 方案 B | 中 | 中度 | 中 | 中 | ⭐⭐ |
| 方案 C | 高 | 廣泛 | 高 | 高 | ⭐ |

**建議選用：方案 A**
理由：[具體說明，禁止只寫「綜合考量後較為合適」這種廢話]
```

### 實作建議格式

每個建議方案應包含：

```
### 方案名稱

**目標：** 一句話說明這個方案要達到什麼效果

**做法：**
- 步驟一
- 步驟二
- ...

**預估成本：** 開發 X 天 / 需要哪些角色配合

**前置條件：** 有沒有什麼事要先做、先確認

**驗收標準：** 怎麼確認做完了、做對了
```

## 5. 優先級排序 (Priority Assessment)

### 優先級矩陣

依「用戶影響」與「實作成本」決定優先序：

| | 成本低 | 成本高 |
|---|---|---|
| **影響大** | 🔴 立即做（Quick Win） | 🟡 計畫排入（需評估） |
| **影響小** | 🟢 有空再做（Nice to have） | ⚫ 暫緩或捨棄 |

### 優先級標記

| 標記 | 定義 |
|------|------|
| `[P0]` | 阻塞用戶核心流程，必須立即處理 |
| `[P1]` | 顯著影響體驗或效能，當前迭代排入 |
| `[P2]` | 有改善空間，非緊急，下個迭代考慮 |
| `[P3]` | Nice to have，有餘裕再做 |

## 6. 風險提示 (Risk Flags)

### 必須標記的風險類型

| 風險 | 說明 |
|------|------|
| **相依性風險** | 此改動是否影響其他功能的正常運作？ |
| **資料風險** | 是否涉及資料結構異動？舊資料的 migration 計畫是什麼？ |
| **效能風險** | 改動後在大量資料或高並發下會不會爆？ |
| **回滾風險** | 萬一上線出問題，能快速回滾嗎？ |
| **使用者習慣風險** | 改動是否破壞現有用戶的操作習慣？需要引導嗎？ |

## 7. 產出標籤與回饋規範 (Output Labels)

### 五級標籤

| 標籤 | 圖示 | 定義 | 行動要求 |
|------|------|------|---------|
| **[BLOCKER]** | 🔴 | 前提資訊嚴重不足、或有根本性問題導致方案無法成立 | **必須先解決，才能繼續分析** |
| **[WARNING]** | 🟡 | 方案有潛在風險、假設可信度低、影響範圍超出預期 | **明確標示，決策者需知情** |
| **[CHORE]** | 🔵 | 文件格式不一致、描述模糊、結構待優化 | **建議修正** |
| **[IDEA]** | 💡 | 超出當前範疇的延伸想法、未來可探索的改善方向 | **供參考，不列入主線** |
| **[PRAISE]** | ✨ | 分析完整、建議精準、推論嚴謹，值得作為範本 | **正面標記** |
| **[NEED_INFO]** | ❓ | 缺乏必要資訊，無法產出可信結論 | **列出具體缺口，發問後再繼續** |

### 回饋原則

- **結論前置**：核心建議放第一句，理由放後面。讓決策者不用讀完全文也能抓到重點。
- **具體可操作**：每條建議必須說清楚「做什麼」和「怎麼做」，禁止只說「這邊需要優化」。
- **禁止廢話句式**：「綜合以上分析」「值得注意的是」「相對而言」— 直接刪掉，說結論。
- **數字說話**：能量化就量化。「慢」不夠，「P95 response time 超過 2s」才夠。
