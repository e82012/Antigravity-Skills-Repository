# API 規格書產生器（RESTful API Spec Writer）

## 核心任務

把使用者給的「需求描述」（可能很簡略、口語化、甚至只有一句話），轉化為一份**嚴謹、可直接交付給工程團隊**的 RESTful API 規格書。

這個技能的價值在於「標準化」與「不偷工減料」——無論需求多簡單，輸出都必須完整覆蓋固定模板的每一個欄位，不能因為「看起來不需要」就省略。

## 工作流程

1. **理解需求**：仔細閱讀使用者描述，識別出需求中隱含的「資源（Resource）」「動作（Action）」「使用情境」。
2. **拆解成獨立 API**：一個需求可能對應多支 API（例如「使用者可以管理自己的收藏清單」可能拆成：新增收藏、刪除收藏、查詢收藏清單三支 API）。每一支 API 都要各自完整套用下方模板，不可合併簡寫。
3. **若需求模糊，先合理假設並標註**：例如欄位型別、是否需要分頁、是否需要驗證身份等，若使用者沒講清楚，依業界常規做出合理假設，並在輸出中以「假設說明」標注，而不是省略該欄位或回頭一直追問打斷使用者。只有在關鍵到完全無法產出（例如完全不知道資源是什麼）時才反問。
4. **嚴格依照〈API 規格書標準模板〉輸出**：見下方模板，逐欄位填寫，欄位名稱、順序、階層都不可更動或刪減。
5. **套用 RESTful 設計鐵則**：見下方〈RESTful 設計規範檢查清單〉，每支 API 產出前都要自我檢查一次。

## RESTful 設計規範檢查清單（產出前自我檢查）

- **資源導向命名**：URL Path 必須是名詞（複數），不可出現動詞。
  - ✅ `POST /orders`　❌ `POST /createOrder`
  - ✅ `GET /users/{userId}/orders`　❌ `GET /getUserOrders`
- **HTTP Method 語意正確對應動作**：
  - `GET`：查詢（不可有副作用）
  - `POST`：新增資源 / 觸發無法用其他 method 表達的動作
  - `PUT`：整筆覆蓋更新（需提供完整資源內容）
  - `PATCH`：部分欄位更新
  - `DELETE`：刪除資源
- **階層式路徑表達資源從屬關係**：`/parents/{parentId}/children/{childId}`
- **複數命名一致**：所有資源集合一律用複數名詞（`/orders` 而非 `/order`）。
- **版本化**：若使用者未指定，預設加上 `/v1` 前綴（例如 `/v1/orders`），並於假設說明中註記。
- **狀態碼語意正確**：
  - `200 OK`（查詢/更新成功）、`201 Created`（新增成功）、`204 No Content`（刪除成功且無回傳內容）
  - `400 Bad Request`（參數錯誤）、`401 Unauthorized`（未驗證）、`403 Forbidden`（無權限）、`404 Not Found`（資源不存在）、`409 Conflict`（資源衝突，如重複建立）、`422 Unprocessable Entity`（驗證失敗）、`500 Internal Server Error`
- **查詢參數用於過濾/排序/分頁，不可用於識別單一資源**：單一資源識別一律走 Path Param。
- **無狀態（Stateless）**：每個請求需自帶完整必要資訊（如身份驗證 Token），不依賴伺服器端 session 狀態。

## API 規格書標準模板（強制格式，不可刪減任何區塊）

完整的標準模板（含每一欄位、表格格式、JSON 範例）已固定於 [`resources/api_spec_template.md`](./resources/api_spec_template.md)。

**每次產出規格書前，務必先讀取該範本檔案，並嚴格依照其標題層級、欄位名稱、順序逐字逐節填寫**，不可自行增減或調整結構。若某欄位確實不適用（例如該 API 沒有 Request Body），仍須保留該標題，並明確寫「無」，**不得直接刪除整個區塊**。

範本包含以下區塊：
1. 功能說明
2. URL Path
3. HTTP Method
4. Params（Path Parameters / Query Parameters）
5. Request Body
6. Response（成功回應 / 錯誤回應）
7. 備註與假設

多支 API 拆解時，範本亦提供「0. 需求總覽」與「附錄：共通規範」兩個輔助區塊，用法見範本檔案內說明與下方〈多支 API 的輸出順序〉。

## 多支 API 的輸出順序

當一個需求拆解為多支 API 時：
1. 先用 2-4 句話總結「資源模型」與「拆出幾支 API、各自用途」作為總覽。
2. 接著依 CRUD 慣例順序輸出每支 API（通常為：Create → Read(List) → Read(Detail) → Update → Delete），每支 API 完整套用上方模板，並以 `---` 分隔。
3. 全部產出完後，若有共通的錯誤碼規範或共通的身份驗證機制，可在最後加一段「附錄：共通規範」統一說明，避免每支 API 重複贅述（但個別 API 的「6.2 錯誤回應」仍須列出該 API 實際會用到的錯誤碼）。

## 重要原則（不可違反）

- **不可省略模板中任一標題層級**，即使內容是「無」也要保留標題與「無」字樣。
- **不可用條列式散文取代表格**：Params 與 Request Body 欄位必須用 Markdown 表格呈現。
- **JSON 範例必須是有效、可解析的 JSON**，欄位需與上方表格定義的欄位一致。
- **錯誤回應不可只寫一種**：至少列出該情境下合理會發生的 2 種以上錯誤（除非該 API 邏輯上真的只可能有一種錯誤，仍須說明原因）。
- **遇到模糊需求時，用合理的業界慣例補完，並在「7. 備註與假設」誠實註記**，不要因為資訊不足就跳過欄位或輸出半成品。
- 若使用者要求的輸出格式並非 Markdown（例如要 OpenAPI/Swagger YAML），仍須先依本模板邏輯思考完整內容，再轉換對應格式輸出，且仍要確保資訊完整度等同於本模板要求的所有區塊。
