# 十種造回饋迴路的方式

[`bug-loop`](../SKILL.md) 階段 1 的揭露參考。大致照順序試——越上面的越便宜、越快、越能留下來當回歸測試。

---

## 1. 失敗測試

在任何搆得到 bug 的**接縫**上寫一個會失敗的測試——單元、整合、e2e 都行。首選，因為它修完之後直接變成回歸測試，不用重寫。

## 2. HTTP／curl 腳本

打一台跑著的開發伺服器。適合 API 層的 bug：request 送進去、response 斷言出來，不用啟動整個前端。

```bash
curl -s -X POST localhost:8000/api/orders -d @fixture.json | jq '.status'
```

## 3. CLI 呼叫加固定輸入

用一份 fixture 輸入跑 CLI，把 stdout 跟一份已知正確的快照比對。適合資料轉換、匯入匯出、報表類的 bug。

## 4. 無頭瀏覽器腳本

Playwright／Puppeteer 驅動 UI，斷言在 DOM／console／network 上。前端專用，比人工點擊快兩個數量級。產物依全局準則 §5 放 `e2e/{任務名}/`，腳本本身放 `tmp/{任務名}/`。

## 5. 重播捕獲的流量

把一筆真實的 request／payload／事件記錄存到磁碟，再單獨重播進那條程式路徑。適合「線上會壞、本地不會壞」，因為它把「環境差異」跟「資料差異」切開了。

## 6. 拋棄式最小載具

拉起系統的一小塊子集（一個服務、其餘相依項用假的），用一次函式呼叫就走完 bug 的程式路徑。當整個系統啟動要好幾分鐘時，這招把迴路從分鐘級壓到秒級。

## 7. 屬性／模糊測試迴路

bug 的症狀是「有時候輸出會錯」時，餵 1000 組隨機輸入，找出那個失敗模式。這招常常順便把最小重現一起找出來。

## 8. 二分搜尋載具

bug 出現在兩個已知狀態之間（commit、資料集版本、套件版本）時，把「切到狀態 X → 檢查 → 重複」自動化，就能餵給 `git bisect run`。

```bash
git bisect start <壞的> <好的>
git bisect run ./tmp/bug-x/check.sh
```

## 9. 差分比對迴路

同一份輸入分別跑過舊版與新版（或兩組設定），比對輸出差異。回歸類 bug 的最短路徑：差異出現的位置就是嫌疑犯的位置。

## 10. 人在迴路裡的腳本

最後手段。真的需要人去點的時候，用腳本**驅動人**——印出「請執行第 N 步，然後按 Enter」，把人的觀察結果收回腳本裡。迴路仍然是結構化的，捕獲到的輸出仍然餵得回代理。

```bash
#!/usr/bin/env bash
# tmp/{任務名}/hitl-loop.sh
set -euo pipefail
for i in $(seq 1 10); do
  echo "[$i/10] 請在 App 裡完成一次結帳，完成後按 Enter"
  read -r
  ./check-symptom.sh && echo "PASS" || echo "FAIL <-- 重現了"
done
```
