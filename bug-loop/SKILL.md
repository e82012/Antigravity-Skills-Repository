# 除錯迴路 (Bug Loop)

給難搞 bug 用的紀律。跳過任何一個階段都必須明說理由。

探索程式碼時先讀 `CONTEXT.md`（若存在），用專案的詞彙建立心智模型，並看過這一區的 ADR。

## 階段 1 — 建一條回饋迴路

**這一階段就是整個技能。** 其餘都是機械操作。只要你手上有一條**緊**的通過／失敗訊號——一條會對**這個** bug 亮**紅燈**的訊號——你就找得到原因；二分搜尋、假設驗證、埋探針全都只是在消費它。手上沒有，盯著程式碼看再久也救不了你。

在這裡不成比例地投入。**要積極、要有創意、不准放棄。**

十種造迴路的方式，大致照這個順序試——完整說明與範例見 [resources/feedback-loops.md](resources/feedback-loops.md)：

失敗測試 → HTTP／curl 腳本 → CLI 加固定輸入比對快照 → 無頭瀏覽器腳本 → 重播捕獲的流量 → 拋棄式最小載具 → 屬性／模糊測試迴路 → 二分搜尋載具 → 差分比對迴路 → 人在迴路裡的腳本（最後手段）。

### 把迴路收緊

把迴路當產品做。有了**一條**迴路之後，**收緊**它：

- 能更快嗎？（快取前置作業、跳過無關初始化、縮小測試範圍）
- 訊號能更利嗎？（斷言在那個具體症狀上，不是「沒有炸掉」）
- 能更確定嗎？（固定時間、固定亂數種子、隔離檔案系統、凍結網路）

一條 30 秒又會飄的迴路，跟沒有迴路差不多；一條 2 秒且每次結果相同的迴路，是除錯的超能力。

### 非確定性 bug

目標不是乾淨的重現，而是**更高的重現率**。把觸發條件跑 100 次、平行跑、加壓、縮小時間窗、注入 sleep。50% 會飄的 bug 除得動，1% 除不動——把重現率一路拉到除得動為止。

### 真的建不出來的時候

**停下來，明說**。列出你試過什麼，然後跟使用者要：(a) 進得去那個能重現的環境、(b) 一份捕獲的證物（HAR、log dump、core dump、有時間戳的螢幕錄影），或 (c) 在正式環境暫時加探針的許可。**沒有迴路就不准往下提假設。**

### 完成判準——一條會亮紅燈的緊迴路

這一階段做完的條件是：你講得出**一行指令**（腳本路徑、測試指令、一行 curl），而且你**已經至少跑過一次**（把指令與輸出貼出來），並且它是：

- [ ] **紅得起來**——它走的是真正的 bug 程式路徑，斷言在**使用者描述的那個症狀**上，所以修好之後它會轉綠。不是「跑起來沒報錯」，是**抓得到這個 bug**。
- [ ] **確定的**——每次跑結論相同（會飄的 bug：釘住一個夠高的重現率）。
- [ ] **快的**——秒級，不是分鐘級。
- [ ] **代理跑得動**——你能無人值守地跑它。

如果你發現自己在有這行指令之前就開始讀程式碼建立理論，**停下來——直接跳到假設正是這個技能要防的那個失敗。** 沒有紅得起來的指令，就沒有階段 2。

## 階段 2 — 重現並最小化

跑迴路，看它亮紅燈。

確認：

- [ ] 迴路產生的是**使用者**描述的那個失敗，不是附近另一個剛好也會壞的失敗。抓錯 bug＝修錯東西。
- [ ] 跨多次執行都重現得出來（非確定性 bug：重現率高到除得動）。
- [ ] 症狀被捕獲下來（錯誤訊息、錯誤輸出、慢掉的耗時），讓後面的階段驗得了修正真的對症。

### 最小化

紅燈之後，把重現縮到**仍然會紅的最小場景**。一次砍一樣——輸入、呼叫端、設定、資料、步驟——每砍一次重跑一次迴路，只留下承重的部分。

值得的理由：最小重現縮小了階段 3 的假設空間，而且它本身就是階段 5 那個乾淨的回歸測試。

**完成判準**：剩下的每一個元素都承重——拿掉任何一個，迴路就轉綠。

沒有同時完成重現與最小化之前，不要往下走。

## 階段 3 — 提假設

在驗證任何一個之前，先產出 **3～5 個排序過的假設**。只想一個假設會讓你錨定在第一個看起來合理的念頭上。

每個假設都必須**可證偽**：寫出它做的預測。

> 格式：「如果原因是 <X>，那麼 <改動 Y> 會讓 bug 消失／<改動 Z> 會讓它更嚴重。」

寫不出預測的，那是感覺，不是假設——砍掉或磨利它。

**排序後的清單先給使用者看再開始驗證。** 他們常常有能瞬間重排的領域知識（「#3 那塊我們昨天剛上線」），或知道哪些已經被排除過。很便宜的檢查點，省很多時間。使用者不在就照你的排序往下走，不要卡住。

**迭代上限**：這一份 3～5 個假設清單整批驗證失敗、要重新提下一輪假設，累計滿 **3 輪**（不是 3 個假設，是 3 批清單）仍未命中，觸發全局準則 §8 的停止條件——列出已排除的假設、已嘗試的探針、建議使用者介入的具體操作點，不要繼續無限提新假設。假設一直錯，通常代表迴路根本沒對到症狀，回頭檢查階段 2 的重現是不是抓錯了 bug。

## 階段 4 — 埋探針

每一根探針都要對應到階段 3 的某一個預測。**一次只改一個變數。**

工具偏好：

1. **除錯器／REPL** 如果環境支援。一個中斷點勝過十行 log。
2. **針對性的 log**，埋在能分辨假設的邊界上。
3. 不要「全部都 log 然後 grep」。

**每一行除錯 log 都加唯一前綴**，例如 `[DEBUG-a4f2]`。最後清場就變成一次 grep。沒標記的會活下來，標記過的死得乾淨。

**效能分支**：效能回歸用 log 通常是錯的。改成先建立基準量測（計時載具、`performance.now()`、profiler、查詢執行計畫），再二分。先量再修。

**提防路燈效應**：假設驗證卡住時，容易一直在方便查的地方加探針（已開啟的檔案、同一個 service），而不是去查真正該查、但比較不方便的地方——另一個 repo 的 middleware、被註解掉的程式碼、設定檔或資料庫裡的值。方便查的地方查完仍找不到，優先懷疑「答案在別處」，不是「這個 bug 沒有原因」（完整規則見 `verification-depth-rules.md` 規則六）。

## 階段 5 — 修正並補回歸測試

回歸測試寫在修正**之前**——但前提是存在一個**正確的接縫**。

正確的接縫，指的是測試在**呼叫端真實發生的那個 bug 模式**上執行。如果唯一可用的接縫太淺（bug 需要多個呼叫端才會發生，測試只測得到單一呼叫端；或單元測試複製不出觸發 bug 的那條鏈），在那裡補回歸測試只會給假的安全感。

**如果不存在正確的接縫，那件事本身就是發現。** 記下來——這代表架構正在阻止這個 bug 被鎖死。

存在正確接縫時：把最小重現變成該接縫上的失敗測試 → 看它失敗 → 套用修正 → 看它通過 → 拿**未最小化**的原始場景重跑階段 1 的迴路。

## 階段 6 — 清場與檢討

宣告完成前必須做到：

- [ ] 原始重現已經重現不出來（重跑階段 1 的迴路）
- [ ] 回歸測試通過（或「沒有正確接縫」這件事已被記錄）
- [ ] 所有 `[DEBUG-...]` 探針已移除（用前綴 grep 一次）
- [ ] 拋棄式載具已刪除（或移到明確標示的除錯位置，依全局準則 §5 放 `tmp/{任務名}/`）
- [ ] 事後證明成立的那個假設，寫進 commit／PR 訊息——讓下一個除錯的人學到

**然後用冰山模型往下問，不要只停在這次的症狀：**

| 層次 | 問題 |
|------|------|
| 事件（剛修完的） | 這次具體是什麼壞了？ |
| **型態** | 同樣的成因，在其他模組是不是也存在？（搜一次同樣的程式碼模式） |
| 結構 | 什麼架構或流程，讓這種成因容易發生？（沒有好的測試接縫、呼叫端糾纏、隱藏耦合） |

事件層是階段 1～5 已經回答的。**型態層最容易被跳過**——修完就想收工，沒人主動去查
「別的地方是不是也這樣壞」。花一次搜尋的成本查一下：找到就在 commit／PR 訊息裡註明
「已核對同型態，其他 N 處⋯」；沒空查就明說「型態層未查」，不要略過不提。

結構層答案牽涉架構時，把具體情況交給架構改善流程。這個建議在**修正進去之後**才提，因為你現在掌握的資訊比開工時多。
