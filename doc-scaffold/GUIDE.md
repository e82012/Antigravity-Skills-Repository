# doc-scaffold 完整填寫指南

> 本指南補充 SKILL.md 的缺口，提供各文件的詳細填寫方法、常見陷阱與決策樹。

---

## 何時產出完整版 vs 簡化版

### 決策樹

```
功能描述是否完整？
├─ 不完整 → 簡化版（三份）
└─ 完整
   ├─ 涉及 API？
   │  ├─ 是 → 需產 api.md
   │  └─ 否 → 可略 api.md
   ├─ 涉及資料異動？
   │  ├─ 是 → 需產 database.md
   │  └─ 否 → 可略 database.md
   └─ 涉及複雜流程？
      ├─ 是 → 建議產 bdd.md
      └─ 否 → 可略 bdd.md
```

### 判斷標準

#### ✅ 必產 api.md（API 文件）

- [ ] 新增或修改 API 路由
- [ ] API 權限與 maintenance_notes 的角色有差異
- [ ] 涉及外部服務整合
- [ ] 涉及 OAuth / SSO 認證邏輯

#### ✅ 必產 database.md（數據文件）

- [ ] 新增或修改資料表
- [ ] 新增或刪除重要欄位
- [ ] 涉及資料遷移 (migration)
- [ ] 涉及複雜的資料異動規則（如軟刪除、狀態轉移等）

#### ✅ 建議產 bdd.md（驗收標準）

- [ ] 核心流程涉及多步驟（3 步以上）
- [ ] 涉及權限檢查或狀態轉移
- [ ] 涉及金流、積分、限紅等高風險操作
- [ ] 涉及專案/客戶特有邏輯

#### ⚠️ 可簡化（仅三份）

- 功能是純前端或純展示邏輯
- 功能只涉及單一表的簡單查詢
- 功能規格仍未確認，預計後續補齊

## 各文件詳細填寫指南

### README.md 填寫指南

#### 1. 功能目的
**目標**：讓讀者在 30 秒內理解「這是什麼、為什麼需要、解決什麼問題」。

❌ **不好的例子**
```md
免費旋轉卡是一個功能。
```

✅ **好的例子**
```md
免費旋轉卡用於激勵會員完成特定任務或購買行動。
系統會根據會員行為自動派發旋轉次數，
也允許運營人員手動派發或調整，
會員可在登入遊戲時自動領取並使用。
```

**填寫檢查表**
- [ ] 說明解決了什麼問題（不只列功能名稱）
- [ ] 說明主要使用場景（至少一個）
- [ ] 若涉及客服/運營操作，需說明運營目的

#### 2. 適用專案表格
**目標**：清楚列出各專案的啟用狀態。

**常見問題**
- Q: 若只有一個專案啟用，是否需要列出？
- A: **是的**，即使只有一個專案，也要列出所有已知的專案，其他填 N/A。

**填寫檢查表**
- [ ] 至少列出一個專案
- [ ] 若某專案未啟用，需說明原因（例如：「目前未導入」）
- [ ] 若某專案有差異，需提示「詳見 project_diff.md」

#### 3. 使用角色與入口
**目標**：讓讀者知道哪些人可以用、如何用。

**常見陷阱**
- ❌ 只寫「Admin」，沒說明是否客服也能用
- ❌ 遺漏系統排程或自動化流程
- ✅ 明確列出所有可能的角色，包括「會員」「客服」「代理」「排程」

**填寫檢查表**
- [ ] 列出所有可能操作此功能的角色
- [ ] 對於「待確認」角色，需說明為何待確認
- [ ] 若涉及排程自動執行，需在這裡提及

#### 4. 影響範圍
**目標**：讓後續維護者知道改這功能會影響哪些部分。

**常見問題**
| 項目 | 說明 | 檢查清單 |
|---|---|---|
| 前台 | 會員是否看到新畫面或流程 | 有新頁面 / 有修改既有頁面 / 無影響 |
| 後台 | Admin/客服是否有新操作 | 有新頁面 / 有修改既有頁面 / 無影響 |
| API | 是否新增或修改 API | 新增 X 個 / 修改 X 個 / 無新增 |
| DB | 是否涉及資料表異動 | 新增表 / 新增欄位 / 無新增 |
| 排程 | 是否有自動化任務 | 新增 / 修改 / 無 |
| 權限 | 是否有新的權限規則 | 新增角色 / 修改權限 / 無 |

### maintenance_notes.md 填寫指南

#### 1. 主要流程
**目標**：讓下一位接手工程師能按照步驟理解功能如何運作。

❌ **不好的例子**
```md
使用者操作功能，系統處理，完成。
```

✅ **好的例子**
```md
1. 會員登入遊戲，系統查詢該會員是否有未領取的免費旋轉卡。
2. 若有，系統自動派發旋轉次數到會員帳戶。
3. 會員在遊戲中選擇免費旋轉卡遊戲並使用旋轉次數。
4. 遊戲完成後，系統扣除使用的旋轉次數並記錄結果。
5. 若使用次數已用完，隱藏免費旋轉卡選項。
```

**填寫檢查表**
- [ ] 流程至少有 3 步以上
- [ ] 每步清楚說明「誰」做「什麼」
- [ ] 涉及系統自動化時，需說明觸發時機
- [ ] 若流程在不同專案有差異，需說明或參考 project_diff

#### 2. 相關程式位置
**目標**：讓工程師快速定位代碼。

**常見陷阱**
- ❌ 填「待補」但永遠沒補
- ✅ 能確認就填，不能確認就標「待補」並說明「無法從規格推断」

**應該如何填**

| 類型 | 範例 | 說明 |
|---|---|---|
| Route | `/app/Http/routes/api.php:234` | 具體行號 |
| Controller | `/app/Http/Controllers/ExampleController.php` | 類名 |
| Service | `/app/Services/ExampleService.php` | 類名 |
| Model | `/app/Models/Example.php` | 類名 |
| Repository | `/app/Repositories/ExampleRepository.php` | 類名 |
| Migration | `/database/migrations/2026_01_01_000000_create_example_table.php` | 具體檔案 |
| 前端文件 | `/frontend/pages/example.vue` | 相對路徑 |
| Job/Queue | `App\Jobs\ProcessExample` | 命名空間 |

**填寫檢查表**
- [ ] 若無法從規格推断，標「待補」而非猜測
- [ ] 重要的路由/方法需標出具體行號，方便快速定位
- [ ] 若涉及多個模組，需列出所有相關位置

#### 3. 特殊規則
**目標**：記錄「不看代碼會漏掉」的規則。

**常見陷阱**
- ❌ 寫「依專案配置」但沒說明具體配置
- ✅ 明確寫出規則，例如「專案 A 優先度為 1，專案 B 為 2」

**應該寫什麼**

| 規則類型 | 範例 |
|---|---|
| 優先順序 | 會員個別設定 > 代理預設設定 > 系統預設值 |
| 生效時機 | 修改後下次登入遊戲才生效（不是立即生效） |
| 權限判斷 | Admin 可設定所有會員，客服只能設定代理下屬會員 |
| 狀態轉移 | 只有 enabled 狀態可修改；disabled 狀態不允許操作 |
| 資料來源 | 若會員個別設定為空，系統應回退到代理設定 |
| 排除規則 | VIP 會員不受此限制；特殊帳戶予以排除 |

**填寫檢查表**
- [ ] 至少列出一條特殊規則（即使只是「目前無特殊規則」）
- [ ] 每條規則都應該影響開發或測試
- [ ] 若規則跨越多個專案，需標記影響範圍

#### 4. 已知問題 / 維護地雷
**目標**：幫助下一位工程師避免重複踩坑。

**應該記錄什麼**

| 問題類型 | 範例 |
|---|---|
| 時序問題 | 資料更新後會員未立即套用，需等待下次登入 |
| 客戶差異 | 不同客戶的邏輯不同，修改共用 Service 需先確認影響範圍 |
| 效能陷阱 | 若查詢未加分頁，大客戶會導致超時 |
| 兼容性問題 | 舊版 App 不支援新欄位，需做版本判斷 |
| 已知 Bug | 某個特定狀態下會出現 Bug，已列為待修復 |

**填寫檢查表**
- [ ] 若無已知問題，明確寫「目前無已知問題」而非留空
- [ ] 每個問題都應包含「影響」「原因」「處理方式」「狀態」

### api.md 填寫指南

#### 1. API 清單表
**目標**：一覽此功能涉及的所有 API。

**填寫規則**

| 欄位 | 說明 |
|---|---|
| **端點** | `/api/v1/example` 的完整路徑（含版本號） |
| **方法** | GET / POST / PUT / DELETE / PATCH |
| **用途** | 一句話說明這個 API 的功能 |
| **權限** | 需要的最低權限（例如：登入 / Admin / 客服） |
| **備註** | 是否只特定專案有、或有特殊限制 |

✅ **好的例子**
```md
| `/api/v2/free-spin/claim` | POST | 領取免費旋轉卡 | 登入 | 若專案 B 無此端點詳見 project_diff |
```

#### 2. Request 與 Response
**目標**：讓前端開發者清楚知道要發什麼、會收到什麼。

**常見陷阱**
- ❌ Response 示例與實際不符
- ❌ 遺漏 nested object 或 array 的結構
- ✅ 示例應該是實際可運行的 JSON

**填寫檢查表**
- [ ] Request 示例應該是有效的 JSON（能複製粘貼測試）
- [ ] Response 示例應該涵蓋成功與失敗情況
- [ ] 若涉及分頁，需展示 pagination 物件
- [ ] 若欄位有多種類型，需說明（例如：status 只能是 "enabled" / "disabled"）

#### 3. 錯誤碼
**目標**：讓前端知道什麼時候會失敗、如何處理。

**填寫規則**

| 欄位 | 說明 |
|---|---|
| **錯誤碼** | 系統定義的錯誤代碼（全大寫，例如：PERMISSION_DENIED） |
| **HTTP 狀態** | 應該回傳的 HTTP 狀態碼（200 / 400 / 403 / 500 等） |
| **說明** | 用戶易懂的說明 |
| **是否寫 Log** | 是否需要在後端記錄此錯誤（高風險操作需寫） |
| **備註** | 例如：「需記錄操作者」「需記錄目前狀態」 |

**常見錯誤碼**

| 錯誤碼 | 說明 | 通常何時出現 |
|---|---|---|
| `VALIDATION_ERROR` | 輸入資料驗證失敗 | 必填欄位為空、格式不正確 |
| `PERMISSION_DENIED` | 無權限 | 用戶沒有該操作的權限 |
| `RESOURCE_NOT_FOUND` | 資源不存在 | 查詢不到指定 ID 的資料 |
| `CONFLICT` | 資源狀態衝突 | 重複送出、版本不一致 |
| `INTERNAL_ERROR` | 系統內部錯誤 | 資料庫異常、外部服務超時等 |

**填寫檢查表**
- [ ] 至少列出 3~5 個常見錯誤碼
- [ ] 高風險操作（金流、權限、刪除）需要標「是否寫 Log」為「是」
- [ ] 若某個錯誤碼會出現在多個 API，需統一定義

#### 4. 權限與認證
**目標**：明確誰能調用這些 API。

**應該說明什麼**

| 項目 | 說明 | 範例 |
|---|---|---|
| **認證方式** | Token / Session / OAuth | Bearer Token in Authorization header |
| **允許角色** | 哪些角色能調用 | Admin / 登入會員 / 客服 |
| **細節權限** | 是否有細粒度的權限控制 | Admin 可查看所有會員，會員只能查看自己 |

### database.md 填寫指南

#### 1. 表結構
**目標**：讓 DBA 或後端工程師能快速建立資料表。

**填寫規則**

| 欄位 | 說明 | 示例 |
|---|---|---|
| **欄位名** | 蛇形命名（全小寫、底線分隔） | `member_info_uid` |
| **型別** | MySQL 型別 | `bigint unsigned`, `varchar(255)`, `json`, `decimal(10,2)` |
| **必填** | 是否可為 NULL | 是 / 否 |
| **預設值** | 若未填時的預設 | `CURRENT_TIMESTAMP`, `enabled`, `null` |
| **主/外鍵** | PK / FK | PK, FK → `member_info(uid)` |
| **說明** | 欄位用途 | 「會員 UID，有會員才填」 |

**常見陷阱**
- ❌ 使用 `float` / `double` 存金額（應用 `decimal`）
- ❌ 時間戳用 `varchar` 而非 `timestamp`
- ✅ 敏感資料加密存儲時需說明加密方式

**填寫檢查表**
- [ ] 是否有 PK（主鍵）？
- [ ] 是否有時間戳欄位（created_at / updated_at）？
- [ ] 若有金額欄位，是否用 `decimal` 而非 `float`？
- [ ] 若有外鍵，是否清楚說明關聯表？

#### 2. 索引
**目標**：說明如何最佳化查詢效能。

**應該何時建立索引**

| 場景 | 索引範例 | 優先級 |
|---|---|---|
| 常用查詢條件 | `status`, `created_at` | **高** |
| 排序欄位 | `created_at DESC` | **高** |
| JOIN 條件 | `member_info_uid` | **高** |
| 複合查詢 | (`status`, `created_at`) | **中** |
| 唯一性約束 | `email` UNIQUE | **高** |

**填寫檢查表**
- [ ] 列出所有常用查詢欄位的索引
- [ ] 若有複合索引，順序是否正確？（選擇性強的欄位在前）
- [ ] 索引總數是否合理？（通常不超過 5~6 個）

#### 3. 資料異動規則
**目標**：說明資料如何被創建、更新、刪除。

**應該定義**

| 規則 | 說明 | 範例 |
|---|---|---|
| **INSERT** | 新增時哪些欄位必填、預設值是什麼 | `status` 預設 `enabled` |
| **UPDATE** | 哪些欄位可修改、哪些不可修改 | `created_at` 不可修改 |
| **DELETE** | 使用軟刪除還是物理刪除、如何處理關聯資料 | 軟刪除：設置 `deleted_at` |
| **交易** | 多表異動時如何保證一致性 | 更新主表 + 記錄日誌需在同一交易內 |

**填寫檢查表**
- [ ] 是否明確說明「軟刪除」或「物理刪除」？
- [ ] 若涉及多表異動，是否有交易說明？
- [ ] 若有並發修改風險，是否有樂觀鎖或悲觀鎖說明？

### bdd.md 填寫指南

#### 1. Feature 描述
**目標**：清楚定義這個功能的目標。

**Gherkin 格式**
```gherkin
Feature: {功能名稱}
  作為 {使用角色}
  我想要 {具體動作}
  以便 {達成目的}
```

✅ **好的例子**
```gherkin
Feature: 領取免費旋轉卡
  作為 會員
  我想要 在登入遊戲時自動領取免費旋轉卡
  以便 可以在遊戲中使用免費旋轉機會
```

#### 2. Scenario 編寫
**目標**：用通俗語言描述各種情況。

**Gherkin 結構**
```gherkin
Scenario: {情境名稱}
  Given {前置條件}
    And {額外條件}
  When {使用者或系統執行動作}
    And {額外動作}
  Then {預期結果}
    And {額外驗證點}
```

**應該涵蓋的 Scenario 類型**

| 類型 | 目標 | 範例 |
|---|---|---|
| **正常流程** | 功能正常運作 | 「成功領取免費旋轉卡」 |
| **異常流程** | 資料驗證失敗 | 「資料不完整時應拒絕」 |
| **權限測試** | 確保權限控制 | 「無權限角色不能操作」 |
| **邊界測試** | 邊界值處理 | 「領取次數為 0 時應隱藏」 |
| **並發測試** | 並發安全 | 「多人同時領取不應重複」 |
| **狀態測試** | 狀態轉移正確 | 「已領取狀態下不可再領」 |

**填寫檢查表**
- [ ] 至少有 4 個 Scenario（正常 + 異常 + 權限 + 邊界）
- [ ] 每個 Scenario 都應該是可測試的（QA 能根據步驟驗證）
- [ ] Scenario 應該與 maintenance_notes 的流程對應

#### 3. 驗收標準
**目標**：清楚定義什麼時候功能算「完成」。

**應該包含什麼**

| 項目 | 說明 | 範例 |
|---|---|---|
| **功能完成** | 所有 Scenario 都通過 | ✅ 正常流程通過 |
| **資料正確性** | 資料庫欄位值正確 | ✅ `status` 欄位被正確更新 |
| **日誌記錄** | 高風險操作有寫日誌 | ✅ 修改操作被記錄 |
| **性能指標** | 查詢時間在可接受範圍 | ✅ API 響應時間 < 1 秒 |
| **跨瀏覽器** | 前端在多瀏覽器上正常 | ✅ Chrome / Firefox / Safari 都正常 |

## 常見陷阱與檢查清單

### 高風險功能必檢清單

若功能涉及以下領域，需特別注意：

#### 💰 金流相關
- [ ] 金額欄位是否使用 `decimal` 而非 `float`？
- [ ] 是否有小數位精度說明（例如：精確到分）？
- [ ] 是否有溢出檢查（例如：最大金額限制）？
- [ ] 異常時是否有回滾機制？
- [ ] 是否寫入金流日誌供審計？

#### 🔐 權限相關
- [ ] 是否清楚定義「查看」與「修改」的權限差異？
- [ ] 是否有角色/代理層級的權限檢查？
- [ ] 是否有「只能修改自己管理範圍內的資料」的限制？
- [ ] 權限檢查失敗是否有寫安全日誌？

#### 🎮 遊戲邏輯相關
- [ ] 投注、限紅、登入流程是否經過多輪測試？
- [ ] 是否考慮了不同遊戲類型的差異？
- [ ] 是否有防重複操作的機制？
