## 正常流程

### Scenario: 成功執行功能

```gherkin
Scenario: 成功執行功能
  Given 使用者已登入且具有操作權限
    And 功能目前為啟用狀態
    And [具體的前置條件，例如：會員的限紅已設定]
  When 使用者送出正確的請求
    And 請求欄位符合所有驗證規則
  Then 系統應成功處理請求
    And 系統應更新相關資料（待補具體欄位）
    And 系統應回傳成功訊息
    And 系統應寫入操作紀錄
    And [其他應驗證的結果]
```

### Scenario: 查詢資料成功

```gherkin
Scenario: 查詢資料成功
  Given 使用者已登入
    And 資料庫中已存在相關資料
  When 使用者查詢該資料
  Then 系統應回傳完整資料列表
    And 回傳的欄位應與 api.md 定義一致
    And 若有分頁，應回傳正確的分頁資訊
```

## 失敗與邊界情境

### Scenario: 權限不足時不可操作

```gherkin
Scenario: 權限不足時不可操作
  Given 使用者已登入但沒有操作權限
    And [例如：使用者只是會員，但嘗試 Admin 操作]
  When 使用者嘗試執行功能
  Then 系統應拒絕操作
    And 系統應回傳 PERMISSION_DENIED 錯誤碼（參見 api.md）
    And 系統應寫入安全審計日誌
    And 不應異動任何資料
```

### Scenario: 資料狀態不允許操作

```gherkin
Scenario: 資料狀態不允許操作
  Given 目標資料目前狀態為 {例如：disabled / archived}
    And 該狀態不允許執行此操作
  When 使用者送出操作請求
  Then 系統應拒絕操作
    And 系統應回傳 STATUS_INVALID 錯誤碼
    And 系統應清楚提示「為什麼不能操作」
    And 系統不應異動資料
```

### Scenario: 資料驗證失敗

```gherkin
Scenario: 資料驗證失敗
  Given 使用者送出的請求欄位不符合規則
    And [例如：必填欄位為空 / 欄位長度超限 / 格式不正確]
  When 系統驗證請求
  Then 系統應回傳 VALIDATION_ERROR 錯誤碼
    And 系統應詳列每個驗證錯誤
    And 系統不應執行任何操作
```

### Scenario: 資料不存在

```gherkin
Scenario: 資料不存在
  Given 使用者查詢或修改不存在的資料
  When 系統進行查詢或修改
  Then 系統應回傳 NOT_FOUND 錯誤碼
    And 系統應提示「資料不存在」
    And 系統不應進行後續操作
```

### Scenario: 重複送出請求

```gherkin
Scenario: 重複送出請求
  Given 使用者已成功送出過相同請求
    And [例如：透過 idempotency key 識別]
  When 使用者再次送出相同請求
  Then 系統應依幂等性規則處理
    And 系統應回傳與第一次相同的結果
    And 系統不應重複異動資料
    And [例如：不應重複扣款 / 不應重複建立記錄]
```

## 高風險情境

### Scenario: 並發修改防護（若涉及樂觀鎖）

```gherkin
Scenario: 並發修改時應防止資料不一致
  Given 使用者 A 與使用者 B 同時修改同一筆資料
  When 使用者 A 先提交修改
    And 使用者 B 後提交修改
  Then 系統應檢測到版本衝突
    And 系統應拒絕使用者 B 的修改
    And 系統應提示「資料已被修改，請重新載入」
    And 使用者 B 需要重新加載資料後再修改
```

### Scenario: 交易回滾（若涉及多表異動）

```gherkin
Scenario: 異動失敗時應完整回滾
  Given 操作需要同時異動主表與日誌表
  When 主表異動成功但日誌表異動失敗
  Then 系統應回滾整個交易
    And 主表應回復到修改前狀態
    And 系統應回傳錯誤訊息
    And 不應留下半套資料
```

### Scenario: 軟刪除驗證（若涉及軟刪除）

```gherkin
Scenario: 軟刪除後的資料不應出現在正常查詢
  Given 資料已被軟刪除（deleted_at 不為 NULL）
  When 使用者進行正常查詢
  Then 系統應排除已刪除的資料
    And 軟刪除資料應只在審計查詢時出現
    And 恢復已刪除資料應需 Admin 權限
```

## 驗收檢查清單

### 功能驗收

- [ ] **正常流程** — 所有成功 Scenario 都通過
- [ ] **權限驗證** — 不同角色的操作限制符合預期
- [ ] **資料驗證** — 所有驗證規則都有檢查
- [ ] **邊界值測試** — 最小值、最大值、邊界值都測過
- [ ] **錯誤處理** — 所有錯誤碼都有對應的測試
- [ ] **重複送出防護** — 幂等性檢查通過（若需要）

### 資料完整性

- [ ] **資料表異動** — 所有預期的欄位都有正確填入
- [ ] **操作紀錄** — 異動都有寫入日誌表（若需要）
- [ ] **時間戳** — created_at / updated_at 都有正確設置
- [ ] **軟刪除** — 查詢時正確排除已刪除資料（若採用軟刪除）

### API 一致性

- [ ] **Request 格式** — API 實際接收的格式與 api.md 一致
- [ ] **Response 格式** — API 實際回傳的格式與 api.md 一致
- [ ] **錯誤碼** — API 回傳的錯誤碼與 api.md 定義一致
- [ ] **HTTP 狀態碼** — 成功/失敗時的狀態碼正確

### 日誌與監控

- [ ] **操作日誌** — 高風險操作都有寫入日誌
- [ ] **Log 格式** — 日誌內容與 maintenance_notes 的 Log 說明對應
- [ ] **錯誤日誌** — 系統異常都有記錄 stack trace

### 性能與並發

- [ ] **查詢性能** — 查詢時間在可接受範圍內（例如 < 1秒）
- [ ] **並發安全** — 多人同時操作不會造成資料不一致
- [ ] **批量操作** — 若有批量操作，不會鎖表過久

### 跨專案驗證

- [ ] **專案 A 流程** — 專案 A 的特有 Scenario 都通過
- [ ] **專案 B 流程** — 專案 B 的特有 Scenario 都通過
- [ ] **邏輯隔離** — 修改某專案邏輯時，不影響其他專案
