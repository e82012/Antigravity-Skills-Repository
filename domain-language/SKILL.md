# 領域語言 (Domain Language)

專案的詞彙表是給代理讀的地圖。這個技能是維護它的紀律：把模糊的詞磨利，把一詞多義拆開，把難以回頭的決策釘成 ADR。

兩份產物，各有分工：

| 產物 | 放什麼 | 位置 |
|------|--------|------|
| `CONTEXT.md` | **詞彙表**——這個專案的名詞是什麼意思 | 倉庫根目錄（monorepo 時每個 package 一份，根目錄放 `CONTEXT-MAP.md` 指過去） |
| ADR | **難以回頭的決策**——脈絡、決策、後果 | `docs/adr/NNNN-標題.md` |

## 什麼時候該動

四種訊號，看到就動，不要留到最後：

- **新詞**：對話裡出現一個 `CONTEXT.md` 沒有的名詞。
- **一詞多義**：同一個詞在不同段落指了不同的東西（例如「帳號」同時指登入身分、錢包、與後台使用者）。這是最值錢的一種——拆開它，通常會連帶拆出一個資料模型問題。
- **繞圈解釋**：你得用一整句話去描述一個概念，而且這句話已經講過第二次。這句話該塌縮成一個詞。
- **難以回頭的決策**：選型、資料模型、對外介面、相容性承諾。

## 怎麼磨一個詞

1. **先拿現況挑戰它**。這個詞在程式碼裡對應到什麼？搜出實際的類別、資料表、函式名。查證依全局準則 §1.3——名稱相似不算數，要讀到實際操作的那一行。
2. **用邊界情境壓力測試**。舉一個這個詞「幾乎適用但不完全適用」的情境問使用者。定義撐不過去，就是定義還不夠利。
3. **一次問一個問題**，等回答再問下一個。
4. **寫進 `CONTEXT.md`**：一行定義，加上「別這樣叫」——列出刻意迴避的近義詞。近義詞不擋掉，共同語言會被稀釋回原點。

## `CONTEXT.md` 的樣子

```markdown
# 專案共同語言

## 物化 (Materialization)
課程結構裡的一堂課從「只存在於大綱」變成「在檔案系統裡有實體位置」的那一步。
_別這樣叫_：建立、初始化、生成
```

只寫**現在是什麼**。詞義的演變史交給 git log——這與全局準則 §10 的文件撰寫準則一致。

## ADR 的樣子

一則 ADR 四段：**脈絡**（當時面對什麼）、**決策**（決定做什麼）、**後果**（因此得到什麼、失去什麼）、**狀態**（提案／已接受／已被 NNNN 取代）。被推翻時不刪舊檔，新開一則並把舊的標成已取代。

## 完成判準

這一輪對話裡出現過的每一個新詞，都在 `CONTEXT.md` 找得到，或被明確判定為不值得收錄；每一個難以回頭的決策，都有一則 ADR 或被明確判定為可回頭。
