# 差異嚴重度分級判準

> 每個查出的差異都要歸類，並寫明「核心邏輯是否實質相異」。分級決定要不要進 Phase 4 修正。

## 三級定義

### ✅ 等價重構（Equivalent）— 不動

架構不同，但**在所有測試輸入下最終輸出逐鍵逐值一致**。

典型情境：
- 整併把原專案內嵌在 Controller／Service 的邏輯，抽成 `OriginV*Report` 策略類，經 Resolver 分派。結構全變，輸出不變。
- 方法名稱不同（`origin` vs `originCagentcheckList`）、參數注入方式不同、檔案位置不同。

處置：記錄「已確認等價」與佐證（動態逐值比對通過），不改任何碼。

### ⚠️ 可接受差異（Accepted Divergence）— 記錄並說明理由

輸出有差，但差異來自**整併刻意的合併／簡化決策**，且該決策有明確、正當的理由。

典型情境：
- 整併統一了多站原本不一致的欄位命名／格式（原專案各寫各的，整併收斂成一套）。
- 修正了原專案已知的 bug（原版輸出其實是錯的，整併改對）——此類要**特別標明**，因為它會讓動態比對 mismatch，但方向是「整併比原版正確」。
- 移除原專案的死碼路徑／已停用功能。

處置：**必須在報告寫清楚**：差在哪個 path、原值 vs 新值、為何這個差是刻意且正當的、是否需要使用者拍板。不得把未查證的 mismatch 隨手歸到這類來規避修正——歸這類的前提是**說得出具體、可驗證的理由**。

### ❌ 整併漏洞（Regression）— 進 Phase 4 修正

輸出不一致，且**不是**刻意決策，是整併過程改錯／漏搬邏輯。

典型情境：
- 某站的特殊 where 條件／幣別換算／四捨五入，在抽成策略類時漏掉或套錯版本。
- Resolver 版本分派表把某站指到錯的 `origin_v?`。
- config 宣告的版本與原專案實際行為不符。
- 邊界處置改變（原版查無資料回空陣列，整併回 404 之類）。

處置：進 Phase 4 修 MK 側，重跑動態驗證直到收斂，並做共用站回歸。

## 判定流程

```
輸出逐值一致？
  ├─ 是 → ✅ 等價重構
  └─ 否 → 差異有無「刻意且可驗證的正當理由」？
            ├─ 有（說得出具體理由）→ ⚠️ 可接受差異（報告寫明理由）
            └─ 無 / 說不出 → ❌ 整併漏洞（進修正）
```

## 硬性要求

- **預設懷疑**：mismatch 的預設歸類是 ❌，要「舉證」才能升級到 ⚠️。舉不出理由不准歸 ⚠️。
- **不可只靠靜態下級**：靜態看起來等價，仍需動態逐值驗證背書才可標 ✅。靜態是必要條件，不是充分條件。
- **每筆差異獨立分級**：一支端點可能同時有 ✅ 與 ❌ 的不同 path，逐 path 判，不要整支端點一個籠統結論。
