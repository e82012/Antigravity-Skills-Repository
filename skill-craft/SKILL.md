# 技能寫作準則 (Skill Craft)

技能存在的目的，是從一個隨機系統裡榨出確定性。**可預測性**——每次執行都走**同一套流程**（不是產出同一份輸出）——是根本德性，底下每一根槓桿都為它服務。

**粗體詞**的完整定義在 [GLOSSARY.md](GLOSSARY.md)，需要時才翻。

## 調用方式

兩種選擇，付兩種不同的代價：

- **模型可調用**：保留 `description`，代理可以自己觸發，其他技能也叫得動它（你當然還是能手動輸入名稱）。代價是**上下文負載**——那行 description 每一輪都躺在 context window 裡。作法：不寫 `disable-model-invocation`，description 寫給模型看，觸發語要豐富（「當使用者⋯⋯時，使用本技能」）。
- **使用者可調用**：把 description 從代理視野裡拿掉，只有你打出名字才叫得動，別的技能也叫不動。上下文負載為零，但花掉**認知負載**——**你**變成那份索引，得自己記得它存在。作法：`disable-model-invocation: true`，description 改寫給人看，一句話講完。

只有在「代理必須自己搆得到」或「另一個技能必須搆得到」時，才選模型可調用。純手動觸發的一律做成使用者可調用，一毛上下文負載都不用付。

使用者可調用的技能多到記不住時，那份堆積的認知負載用**路由技能**解：一個使用者可調用的技能，列出其他技能各自何時該用。本技能組的路由是 `skill-map`。

> ⚠️ `disable-model-invocation` 是 Claude Code 支援的欄位。Antigravity 是否支援未經查證，所以本技能組的 user-invoked 技能，description 一律寫成「人讀得懂、同時也能當觸發語」——欄位被忽略時行為仍然正確。

## 寫 description

模型可調用的 **description** 幹兩件事：講清楚這技能是什麼，以及列出該觸發它的**分支**。每個字都在加上下文負載，所以 description 要比本文修得更兇：

- **把引導詞放到最前面**——description 是它發揮觸發作用的地方。
- **一個分支一個觸發語**。同一個分支換句話說是**重複**：「用 TDD 建功能⋯⋯要求測試先行」是同一件事寫兩遍。合併掉，只留真正不同的分支。
- **本文已經講過的身分敘述就刪掉**。description 只留觸發語，加上「當其他技能需要⋯⋯」這類轉介條款。
- 使用者用中文下指令，**中文觸發語必須寫進去**，不能只放英文術語。

## 資訊階層

技能由兩種內容組成——**步驟**與**參考**——兩者自由混用：可以全是步驟、全是參考，或兩者都有。核心決策是用哪一種、以及各自落在**資訊階層**的哪一層。這道階梯依「代理多急著要」排序：

1. **技能內步驟**——`SKILL.md` 裡有順序的動作，最上層：代理要做什麼、依什麼順序。每個步驟結束在一個**完成判準**上。判準要**可檢核**（代理分得出做完與沒做完嗎？），必要時要**窮盡**（寫「每一個被改到的模型都交代過」，不要寫「產出一份異動清單」）——判準模糊就是在邀請**過早完成**。
2. **技能內參考**——`SKILL.md` 裡的定義、規則或事實，按需查閱。經常是一組合法的扁平同級項（一次審查的每條規則都在同一層），這是正常編排，不是壞味道。*本技能全篇都是參考。*
3. **外部參考**——把參考推出 `SKILL.md`，放進獨立檔案，靠**上下文指標**指過去，指標被觸發時才載入。

推太少，頂層會腫；推太多，會把代理真正需要的東西藏起來。這個張力就是全部的難處。

**漸進揭露**就是往階梯下方搬的動作。判斷準則用**分支**最乾淨：每條路徑都要的就內嵌，只有部分路徑才碰的就推到指標後面。**上下文指標的「措辭」——不是它指向誰——決定代理何時搆過去、以及搆得多可靠。**

階梯決定一段內容**放多下面**，**共置**則決定它**旁邊擺什麼**：把一個概念的定義、規則、注意事項收在同一個標題下，讀到其中一段就會順帶讀到鄰居。

## 何時該拆

**顆粒度**是你把技能切多細。每切一刀就花掉兩種負載其中之一，所以刀要切得值得。兩種切法：

- **依調用方式切**——當你有一個獨立的**引導詞**該單獨觸發它，或另一個技能必須搆得到它時，切出一個模型可調用技能。你得為那行常駐的 description 付**上下文負載**，這份獨立可及性要值回票價。
- **依順序切**——當後面還沒做的步驟（**後續步驟**）會誘使代理草草結束眼前這一步（**過早完成**）時，把步驟序列切開。看不見後面，代理才願意在當前任務上多做**功課**。

## 修剪

每個意思只留一個**單一真實來源**：一個權威位置，改行為時只要改一處。

逐行檢查**相關性**：這行到現在還跟技能要做的事有關嗎？

然後逐句（不是逐行）獵殺 **no-op**：把每個句子單獨拿出來做 no-op 測試，一旦沒通過，整句刪掉，不要改寫。要狠——沒通過的散文絕大多數該刪，不是該重寫。

## 引導詞

**引導詞**是模型預訓練裡已經存在的壓縮概念，代理執行技能時會用它來思考（例如：*紅燈*、*曳光彈*、*接縫*、*戰爭迷霧*）。整份技能反覆使用同一個詞，它會累積出分散式的定義，用最少的 token 錨定一整區行為——因為它徵用的是模型本來就有的先驗。

它替可預測性服務兩次。在本文裡錨定**執行**：這個詞每次出現，代理都伸手去拿同一套行為。在 description 裡錨定**觸發**：當同一個詞同時活在你的 prompt、文件與程式碼裡，代理會把這套共同語言連到技能上，觸發得更可靠。

主動去找可以重構成引導詞的地方。同一個意思在三個地方各寫一遍（**重複**）、description 花一整句去比劃一個概念——每一處都在求你**塌縮**成一個詞：

- 「快速、確定、低成本」→ *tight*（緊）——同一個特質在一個階段裡被重述三次，塌縮成一個預訓練詞（一條*緊*的迴路）。
- 「一條你信得過的迴路」→ *紅燈*——把模糊的門檻換成二元可觀測狀態（迴路對這個 bug 亮紅燈，或沒有）。

假設每個技能都藏著可以被引導詞退休掉的重述，然後去把它找出來。

## Bitter Lesson：技能會過期

今天精心寫進技能的每一條規則，都會隨模型變強而逐步不再需要。模型每次變強，某些補強措施就該被移除——過時的規則不只是死重量，還可能限制模型發揮新獲得的能力（例如硬性規定的步驟順序，攔住了模型現在已經會自己判斷的路徑）。

**該做的不是「越積越厚」，是每次新模型上線時，回頭問一次「這條規則現在還改變行為嗎？」** 這正是 no-op 測試，只是換了觸發時機：不只是寫技能當下要測，模型換代之後也要重新測一次——同一句話，半年前是 no-op 測試沒過的必要指令，半年後可能已經變成 no-op。

觸發時機：主力模型換代時、技能檔明顯變厚時、或發現某條規則連續多次沒被觸發時，回頭跑一次修剪（見上一節）。這是**沉積**的解藥——沒有主動觸發，修剪不會自己發生。

## 失敗模式

用這幾條診斷使用者遇到的問題。

- **過早完成**——步驟還沒真的做完就收工，注意力滑到「做完了」本身。處置依序：先磨利完成判準（便宜、局部）；只有在判準真的無法再精確**而且**你確實觀察到搶快時，才用拆序列的方式把後續步驟藏起來。
- **重複**——同一個意思出現在不只一個地方。既花維護成本與 token，又會把那個意思在階梯上的份量灌得比它實際位階高。
- **沉積**——陳舊的層次堆著沒清，因為新增感覺安全、刪除感覺危險。任何沒有修剪紀律的技能的預設下場。
- **膨脹**——技能單純就是太長，就算每一行都還活著、都不重複。傷可讀性與可維護性，也浪費 token。解法是階梯：把參考揭露到指標後面，依**分支**或順序拆開，讓每條路徑只帶自己要的東西。
- **No-op**——這行講的事模型本來就會做，你付了負載卻什麼也沒說。測試方法：這行相對於預設行為，有改變任何東西嗎？太弱的引導詞就是 no-op（代理本來就算細心，你還寫「請仔細」），解法是換更強的詞（「毫不留情」），不是換技術。
- **否定式提示**——用禁令操舵會反效果：「別想大象」把大象叫進了場，讓它更容易被想起，不是更少。改用**正面陳述**——直接寫出目標行為，讓被禁的那個從頭到尾沒被講出來。禁令只保留給無法正面表述的硬護欄，而且即使那時也要配一句「那該做什麼」。
