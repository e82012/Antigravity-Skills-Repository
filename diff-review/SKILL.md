# 雙軸差異審查 (Diff Review)

**乾淨地實作錯功能，跟髒亂地實作對功能，是兩件不同的事。** 把兩軸分開，其中一軸才不會遮蔽另一軸——一份漂亮的重構讀起來很順，很容易讓人忘了它根本沒做到工單要求的事。

## 步驟

### 1. 釘住定點

先確定要審什麼。跟使用者確認基準點（commit SHA、分支、tag），預設是分岔點：

```bash
git merge-base HEAD main
git diff --stat $(git merge-base HEAD main)..HEAD
```

**完成判準**：diff 非空，而且你講得出這次改動涵蓋哪幾個檔案、幾行。diff 是空的就停下來說明，不要往下審。

### 2. 找出兩軸的來源

- **規格來源**：這次改動的原始工單／規格／PRD／對話。找不到就問使用者要，不要自己腦補一份需求然後拿它當標準去審。
- **規範來源**：專案自己的程式碼規範。本倉庫的 `code-review` 技能就是規範軸的**外部參考**——直接引用它的判斷準則與五級回饋分級（`[BLOCKER]` `[WARNING]` `[CHORE]` `[IDEA]` `[PRAISE]`），**不要在這裡重抄一份**。專案另有自己的規範文件時，**專案規範優先**。

### 3. 平行跑兩個 sub-agent

兩個 sub-agent 各自只拿到自己那一軸的材料，同時開跑。分開跑的理由是**避免 context 互相污染**：讓同一個 agent 依序審兩軸，第一軸的結論會替第二軸定調。

**規範軸 sub-agent** 拿到：diff、規範來源。它只回答「這段程式碼有沒有照這個專案的方式寫」。專案沒有成文規範時，退回一組壞味道基線：可疑命名、重複程式碼、依戀情結、資料泥團、基本型別偏執、重複的 switch、霰彈式修改、發散式變化、投機性通用化、訊息鏈、中間人、被拒絕的遺贈。**已經被 linter／formatter 擋掉的規則就跳過**——工具管得動的事不佔人的注意力。

**規格軸 sub-agent** 拿到：diff、規格來源。它只回答「這段程式碼有沒有忠實實作那份規格」。它要找的是：規格要求了但沒做的、規格沒要求卻做了的、行為與規格描述有出入的。

### 4. 並列呈現，不跨軸重排

兩軸的發現**並排列出**，各自依嚴重度排序，**不要把兩軸混在一起重新排名**。一次改動可以在一軸過關、在另一軸不及格，混排會把這件事洗掉。

輸出格式：

```markdown
## 規範軸
- [BLOCKER] `app/Services/OrderService.php:88` — ⋯⋯

## 規格軸
- [BLOCKER] 規格 §3.2 要求逾時自動退款，diff 裡找不到對應實作
```

### 5. 完成判準

diff 裡的**每一個檔案**都被兩軸各看過一次；每一條發現都指得出具體的檔案與行號（規格軸則指得出規格的哪一段）。「大致看過沒問題」不算完成。

## 查證紀律

每一條發現都要引用實際的那一行程式碼當證據。宣稱「這裡沒有處理 X」之前，先確認 X 沒有在別的地方被處理掉——這是全局準則 §1.3 的三步查證，只驗證「我沒在這個檔案看到」不算數。

**提防路燈效應**：兩軸都容易只看 diff 裡改動的那幾行，因為那是最方便看的地方。但改到公開介面（函式簽章、API 路由、共用設定）時，真正受影響的呼叫端常常不在 diff 裡——追一次呼叫鏈，不要只看 diff 高亮的部分（完整規則見 `verification-depth-rules.md` 規則六）。
