# 依票實作 (Implement)

把一張票或一份規格做出來。這個技能本身很薄，它的價值在於**固定住順序**：先對齊、再紅綠、最後審查，中間不跳步。

## 步驟

1. **載入脈絡**。讀這張票／規格、`CONTEXT.md`、以及會動到那一區的 ADR。**完成判準**：你能用專案的詞彙複述這張票要打穿哪條路徑，以及要測哪幾個接縫。

2. **確認接縫**。票裡寫的接縫拿出來跟使用者確認一次。票裡沒寫接縫，現在就問——**一次問一個問題**。沒確認過的接縫不寫測試。

3. **紅綠循環**。在確認過的每一個接縫上驅動 `tdd`，一次一片垂直切片：一個測試 → 剛好夠讓它綠的實作 → 下一片。不要先把測試全部寫完。

4. **收尾審查**。跑 `diff-review`，兩軸都看過。規範軸的 `[BLOCKER]` 與規格軸的任何缺漏都要處理掉才算完。

5. **驗證能跑**。執行專案的驗證指令（lint、測試、型別檢查），確保不只「寫對」而且「跑得動」。這是全局準則 §6 的完工定義——守的是**沒有破壞既有行為**，跟下一步守的東西不同。

6. **裁判驗收**。跑 `outcome-check`——派一個全新 context 的裁判，拿票上的驗收條件實際操作產出。這一步守的是**這張票要的新行為真的做到了**：步驟 5 的 lint／測試會綠燈，不代表這張票的驗收條件被滿足——測試綠燈只證明沒有已知的東西被打壞，不證明新東西真的對。**這一步不能省略、不能自己代替裁判判定**：寫這張票的 agent 判自己做完了沒是自我審計，獨立性為零，正是這個步驟要避免的事。連續 3 輪不過，依 `outcome-check` 的迭代上限停下來問使用者。

7. **commit**。訊息寫清楚做了什麼、對應哪張票、裁判判定通過的依據。**使用者沒要求就不要 push**。

## 完成判準

這張票的每一條驗收條件都被 `outcome-check` 的裁判**實際操作驗證**過，不是「跑過的指令與輸出看起來對」——那仍然是同一個 agent 自己判自己。有任何一條做不到，明說是哪一條、卡在哪。

## Context 衛生

一張票一個乾淨的 session。做完一張就清掉 context 再開下一張——上一張票的實作細節留在 context 裡，只會讓下一張票的判斷被舊脈絡帶偏。
